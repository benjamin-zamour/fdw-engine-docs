Écrire un plugin

Tout ce que montre l’éditeur vient de plugins : le viewport, l’outliner, l’inspecteur, les menus File et Edit sont des plugins intégrés. Un hôte ajoute les siens de la même façon. Ce tutoriel en écrit un, Isolate :

  • une commande qui cache tout sauf la sélection, une autre qui remontre tout, dans le menu Edit, avec les touches I et Maj+I ;
  • un panneau Statistics, qui compte les nœuds du niveau par sorte ;
  • un élément de la status bar, tant que la sélection est isolée.

Il tourne dans l’éditeur ci-dessous. Sélectionnez un objet ou deux, puis appuyez sur I (ou Edit → Isolate the selection) ; Maj+I remontre tout. Le panneau Statistics est un onglet du dock droit, à côté de l’Inspector.

Ouvrir l'éditeur dans une page à lui

Le plugin est le package @fdw/editor-plugin-isolate ; tout son code est en fin de page.

1. Le manifeste

Section intitulée « 1. Le manifeste »

Un plugin est d’abord un manifeste : ce qu’il ajoute à l’éditeur, déclaré sans code. L’éditeur le lit au démarrage, et montre aussitôt les commandes, le panneau, les menus et les touches ; le code n’est chargé qu’à l’usage de l’un d’eux.

  • id préfixe chaque contribution : deux plugins ne peuvent pas prendre les mêmes identifiants. engine est la plage des versions de l’API de l’éditeur pour laquelle le plugin est écrit ; un plugin d’une autre plage est refusé, comme un manifeste qui n’est pas valide (le panneau Plugins dit pourquoi).
  • Les commandes ont un titre et une catégorie, montrés dans les menus et dans la palette de commandes (Isolate: Isolate the selection), et une icône parmi celles de l’éditeur (editorIcons, de lucide), connue avant le chargement du code.
  • enablement est une clause when, comme dans VS Code : la commande est désactivée tant qu’elle est fausse, dans les menus, la palette et pour ses touches. Elle lit des context keys : scene.hasSelection est celle de l’éditeur, isolate.active celle du plugin (plus bas).
  • Les menus sont nommés : menubar.edit est le menu Edit du plugin du niveau. Les éléments sont triés par groupe, et les groupes séparés.
  • La vue est un panneau du dock droit, ouvert dans le layout par défaut (open) ; sinon le menu View la montre.
  • Les touches valent tant que leur clause tient : ici, tant que le viewport montre le niveau.

2. Le plugin et son code

Section intitulée « 2. Le plugin et son code »

Le plugin est son manifeste, et une fonction qui charge son code. Avec un import(), le bundler en fait un chunk à part, chargé au premier événement qui en a besoin : une commande lancée, un outil activé, son panneau montré — ici dès le démarrage, puisque son panneau est dans le layout par défaut. Un plugin sans panneau ouvert ne coûte rien avant d’être utilisé.

Le code exporte activate, appelée une fois chargé, avec le contexte du plugin : ses services, et les enregistrements, chacun vérifié contre le manifeste (enregistrer une commande qu’il ne déclare pas lève une erreur).

activate est appelée avant que l’éditeur soit entièrement fait : elle enregistre, et ne lit les services qu’à l’exécution de ses commandes.

3. Lire le niveau

Section intitulée « 3. Lire le niveau »

Le niveau vit dans le moteur, qui peut tourner dans un autre processus : la page ne le tient jamais. Elle en tient la projection, mise à jour par les messages du moteur : le service ILevelStore, un store de @xstate/store. Son contexte a l’arbre par identifiants (nodes, root), la sélection (le nœud actif en dernier), les propriétés du nœud actif, les libellés des prochains annuler et rétablir.

Les nœuds à cacher sont ceux sous la racine qui ne contiennent rien de la sélection — un pied sélectionné garde sa table :

4. Modifier le niveau

Section intitulée « 4. Modifier le niveau »

La page ne modifie le niveau que par des commandes, envoyées au moteur (IEngineConnection) : level.command, avec la commande des outils d’édition à exécuter. Chacune est une étape de l’historique du niveau : Ctrl+Z l’annule.

Les autres commandes : undo, redo, delete (la sélection), add (un nœud vide, un cube, une sphère, une lumière), edit (le nom, la visibilité, la transformation, les champs d’un composant), reparent, select, frame. Le moteur répond par les changements de la projection ; l’outliner et le panneau Statistics suivent.

5. Les commandes et une context key

Section intitulée « 5. Les commandes et une context key »

Les handlers des deux commandes. La première pose la context key isolate.active, jusqu’à ce que la seconde la retire : les clauses du manifeste la lisent, et l’éditeur active la bonne commande sans que le plugin ait à prévenir les menus.

Une commande se lance depuis son menu, sa touche, la palette, ou depuis le code : context.commands.execute(id).

6. Le panneau

Section intitulée « 6. Le panneau »

Une vue est un composant React, enregistré pour la vue du manifeste. Les hooks de @fdw/editor-ui lui donnent l’éditeur : useEditor() le runtime (ses stores, ses services), useSelector(store, select) une partie d’un store, rendue à nouveau quand elle change, useWhen(clause) une clause.

Les composants de l’éditeur (Button, Input…) sont ceux de shadcn/ui, sur Tailwind : les classes du plugin sont données au Tailwind de l’application par sa feuille de style (plus bas).

Pour aller plus loin

Section intitulée « Pour aller plus loin »
  • Un outil : un plugin peut donner un outil, une machine XState dans un emplacement de l’éditeur (primary ou secondary) : Échap le termine, et son état est gardé avec le layout. Le plugin d’exemple, @fdw/editor-plugin-sample, en a un qui pose des marques.
  • Son état : context.state garde une valeur JSON avec le layout, même quand le plugin manque (usePluginState en React). Les identifiants des nœuds sont ceux d’une session du moteur : le plugin ci-dessus ne les garde qu’en mémoire.
  • Ses propres services : context.services est une portée à lui, où il enregistre ce que d’autres plugins peuvent utiliser.
  • Les plugins tournent dans la page, avec ce qu’elle peut faire : ils sont de confiance.
