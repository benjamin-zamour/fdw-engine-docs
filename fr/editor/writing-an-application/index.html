Créer une application web sur l’éditeur

Une application construite sur l’éditeur fournit un profil, des plugins, les parties de ses plugins qui tournent avec le moteur et les scènes dont elle a besoin. Le SDK fournit l’hôte web du moteur, le viewport, les dialogues de fichiers du navigateur et le stockage IndexedDB ; la coque reste EditorShell. Pour une application Electron, consultez le tutoriel desktop dédié.

Le SDK propose des points d’entrée séparés pour le web et le desktop. Ce tutoriel est le projet que la CI construit hors du dépôt, depuis les archives npm des packages : ce qui suit s’installe, se vérifie, se construit et s’exécute tel quel.

Section intitulée « 2. Définir le profil de l’application »

Le profil appartient à l’application, pas à la table des profils intégrés de l’éditeur. Incluez les plugins intégrés nécessaires à la coque, le plugin de cette application et le plugin en package de l’étape 5 :

Le profil restreint l’interface de la coque ; ce n’est pas une frontière de sécurité. Les plugins intégrés à une application sont du code de confiance. Consultez Profils et vues pour les règles d’autorisation des commandes et le comportement de la disposition.

3. Ajouter une extension moteur

Section intitulée « 3. Ajouter une extension moteur »

La partie d’un plugin qui tourne avec le moteur est une extension moteur : elle voit la scène affichée, travaille avant chaque image et échange des messages avec son plugin sous l’identifiant du plugin. Celle-ci compte les images et répond quand son plugin le lui demande :

Sur le web, le moteur tourne dans la page ; dans une application desktop, dans son processus moteur. Les messages sont les mêmes : des valeurs clonables, et des octets en Uint8Array au besoin.

L’application passe ce plugin à son hôte, et l’extension à son moteur. Le profil sélectionne le plugin ; il ne l’installe ni ne le découvre.

6. Laisser un plugin hors d’un profil

Section intitulée « 6. Laisser un plugin hors d’un profil »

L’hôte peut recevoir plus de plugins que le profil n’en sélectionne : un seul build pour plusieurs profils, par exemple celui d’un relecteur et celui d’un administrateur. Un plugin que le profil ne liste pas n’est pas enregistré : ses commandes et ses panneaux n’apparaissent nulle part, et son load ne s’exécute jamais. Avec un import() dynamique, son code reste dans un chunk à part, que la page ne télécharge jamais.

Le profil sélectionne l’interface, ce n’est pas une frontière de sécurité : le code d’un plugin laissé de côté fait toujours partie du site déployé.

7. Assembler et démarrer l’application web

Section intitulée « 7. Assembler et démarrer l’application web »

startWebApplication démarre l’application en un appel : le moteur sur un canvas avec les scènes et les extensions de ses plugins, l’hôte avec son profil et ses plugins (IndexedDB, les dialogues de fichiers du navigateur), la coque rendue dans #root, et le moteur arrêté quand la page s’en va.

Remplacez createShadowsScene par les factories de scènes de votre application. Le backend WebGPU est préféré et WebGL2 peut prendre le relais ; l’option backend permet d’en choisir un explicitement. Le panneau « À propos » affiche la scène et les images comptées par l’extension.

L’adresse de la page prend les options de lancement du SDK (readLaunchOptions) : ?backend=webgl2, ?scene=, ?open=<url> (un modèle ouvert au démarrage ; l’option open en donne un par défaut), ?view= (un panneau ouvert), ?docks=bottom,right, ?embed (rien n’est gardé), ?api (piloté par la page autour du cadre, par @fdw/viewer-embed). onRuntime reçoit le runtime une fois fait, pour ce qui est propre à l’application.

La coque garde la disposition de chaque profil dans le stockage de l’hôte (IndexedDB sur le web, un fichier des données de l’utilisateur sur le desktop) : les panneaux ouverts et fermés, les docks et les barres d’outils se retrouvent au démarrage suivant. View → Reset layout rétablit la disposition du profil. ?embed ne garde rien.

Pour un hôte à vous (un autre stockage, une autre racine, du React autour de la coque), assemblez vous-même WebEngine, createWebHost et EditorShell : startWebApplication en est fait.

Les produits du dépôt sont construits ainsi, et se lancent chacun par une commande : npx nx dev viewer, npx nx dev review, npx nx dev material-editor, npx nx dev game-editor, npx nx dev simulation (Les règles d’architecture).

8. Construire et déployer

Section intitulée « 8. Construire et déployer »

Utilisez les commandes Vite habituelles :

Le site construit est statique et peut être déployé sous un sous-chemin avec l’option base de Vite (npx vite build --base /acme/). Ajoutez cette page vide dans public/, que Vite copie à la racine du site : l’hôte l’ouvre pour afficher les panneaux détachés dans une autre fenêtre.

Les packages ne sont pas encore publiés sur npm. Pour les essayer, empaquetez-les depuis le dépôt avec node tools/sdk/pack.mjs, puis installez les archives de tmp/sdk-package/archives à la place des noms de packages ; node tools/sdk/verify-external.mjs fait tout cela sur ce tutoriel. Pour une application desktop, continuez avec le tutoriel desktop, qui reprend le profil, le plugin et l’extension de celui-ci.
