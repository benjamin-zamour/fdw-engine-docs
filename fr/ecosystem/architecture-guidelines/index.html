Les règles d’architecture

Le dépôt est un ensemble de plateformes (le moteur, l’éditeur), de fondations indépendantes (shared, conversion, geometry), de produits qui les assemblent (apps/) et de labs qui les essaient. Cette page donne les règles pour placer du code. Lisez-la avant d’ajouter un package ou d’en déplacer un ; La structure du dépôt montre le résultat.

Les domaines

Section intitulée « Les domaines »
Domaine Possède Ne possède pas
shared/ Ce dont tous les domaines ont besoin et qu’aucun ne possède : les capabilities, l’état de vue Du code utilisé par deux produits : il a un propriétaire
conversion/ Le modèle pivot : scènes 3D et modèles CAO en mémoire, les rapports de conversion Les formats qui demandent le noyau : geometry/
geometry/ Le noyau géométrique, ses implémentations (OpenCascade), les lecteurs des formats exacts Les maillages pour le GPU : engine/
engine/ Le runtime : rendu, backends, scène, ressources, modules, adaptateurs, ses extensions Toute interface utilisateur, tout DOM dans son cœur
editor/ La plateforme sur laquelle les produits sont construits : interface, SDK et ses hôtes, éditeur de graphes, projet, plugins partagés Les fonctionnalités d’un produit : apps/<produit>/
labs/ Les démos (du moteur, de l’éditeur sur son SDK), leurs scènes, les expérimentations et les prototypes Tout ce dont un produit a besoin pour tourner
apps/ Les produits vendus aux clients, un dossier chacun, avec leurs plugins privés ; la documentation Du code dont un autre produit a besoin : il descend

Deux questions décident du domaine d’un package :

  1. Que connaît-il ? Un package qui dessine connaît le moteur ; un package avec des panneaux React connaît l’éditeur. Il va dans le domaine le plus bas qui contient tout ce qu’il importe.
  2. Qui l’utiliserait seul ? Le pivot sert à des convertisseurs sans le moteur : il reste hors d’engine/. Un lecteur STEP a besoin du noyau : il est dans geometry/, pas dans conversion/.

shared/ est l’exception, pas le choix par défaut : un package n’y va que s’il ne dépend de rien et qu’aucun domaine n’en est un meilleur propriétaire. Être utilisé par deux domaines n’est pas une raison.

Les dépendances

Section intitulée « Les dépendances »

Les domaines sont des couches. Une bibliothèque ne dépend que de son domaine et de ceux d’en dessous :

Une bibliothèque de Peut importer
shared shared
conversion shared, conversion
geometry shared, conversion, geometry
engine shared, conversion, geometry, engine
editor shared, conversion, geometry, engine, editor
labs, apps Tout, sauf une application

Et quel que soit le domaine :

  • Aucune bibliothèque n’importe les labs ni une application. L’éditeur ne prend pas une scène de démo pour remplir son niveau d’exemple : les primitives dont il a besoin sont dans engine-core, le contrat d’une scène qui tourne dans engine-runtime.
  • Le moteur ne connaît pas l’éditeur. L’édition côté moteur (engine-editing, engine-graph-editing) n’a pas de DOM ; l’éditeur s’appuie dessus.
  • Le moteur lit le pivot par des adaptateurs. engine-pivot et engine-gltf font des modèles pivot des ressources du moteur, et inversement ; le pivot porte les graphes de matériaux comme des données (MaterialGraphDocument), que l’adaptateur vérifie avec parseGraph.
  • Un test suit les mêmes règles. Un test qui a besoin d’un domaine plus haut vit dans un package de ce domaine : la fin du tutoriel STEP, écrite en glTF, est testée par engine-pivot, pas par pivot-step.
  • Pas de cycle : le graphe est en couches.

Le lint les vérifie : @nx/enforce-module-boundaries dans eslint.config.mjs lit le tag scope: de chaque projet et refuse un import qui remonte. npx nx run-many -t lint le lance, la CI aussi. Quand le lint refuse un import, déplacez le code dans le bon domaine ou inversez la dépendance (une interface en bas, son implémentation en haut) : n’élargissez jamais la règle pour un package.

Les plugins

Section intitulée « Les plugins »

Il n’y a pas de système de plugins pour tout le dépôt : chaque plateforme a son contrat, et ses plugins vivent avec elle.

Où Propriétaire Pour
engine/plugins/ Moteur Des extensions du runtime chargées par un mécanisme de plugin
editor/plugins/ Éditeur Les plugins partagés par les applications construites sur l’éditeur
apps/<produit>/plugins/ Le produit Les plugins privés d’un produit
  • Une implémentation n’est pas un plugin. engine-physics-rapier implémente l’API d’engine-physics : c’est un package d’engine/, pas d’engine/plugins/.
  • Un plugin naît là où il sert. Un plugin écrit pour un produit va dans apps/<produit>/plugins/. Ne devinez pas une réutilisation future.
  • Un plugin utilisé par un second produit est promu dans les plugins de sa plateforme, après avoir vérifié qu’il ne dépend de rien de son produit : node tools/repo/move.mjs apps/<produit>/plugins/<nom> editor/plugins/<nom>.
  • Un plugin partagé n’importe jamais un produit. C’est le produit qui le configure.

L’éditeur est une plateforme

Section intitulée « L’éditeur est une plateforme »

L’éditeur n’est pas un produit : c’est la plateforme sur laquelle les produits sont construits, par son SDK (@fdw/editor-application-sdk). Le SDK porte les hôtes : /web (le moteur dans un canvas, l’hôte du navigateur, le stockage, les dialogues de fichiers) et /desktop (l’hôte Electron, la connexion au processus du moteur, la session du moteur) ; editor-native-viewport donne le viewport natif. Un produit fournit son profil, ses plugins et ses scènes, et choisit les hôtes avec lesquels il est livré.

  • Les éditeurs du dépôt sont des démos. labs/editor-web et labs/editor-desktop montrent la plateforme sur le SDK : tous les profils, les plugins, les scènes de démo. Ils ne sont pas livrés, et rien ne les importe.
  • Un produit se construit comme eux, dans apps/<produit>/, sur le SDK et les plugins partagés, jamais sur le code d’une démo.
  • Ce qui dépend de la plateforme reste dans les hôtes. Un produit demande à l’hôte les fichiers, le stockage, les fenêtres ; il n’importe ni Electron ni les API du navigateur lui-même. Ce qui manque à un hôte s’ajoute au SDK.

Les labs

Section intitulée « Les labs »

labs/ contient ce qui explore ou montre les capacités : les démos, les scènes qu’elles partagent, les expérimentations, les prototypes.

  • Les labs tournent dans la CI : être expérimental ne dispense pas de compiler ni de ses tests.
  • Aucun produit ne dépend des labs. Un morceau de démo dont un produit a besoin descend d’abord dans son domaine (comme les primitives sont descendues dans engine-core).
  • Les benchmarks de l’infrastructure de mesure restent dans tools/bench/.

Les produits

Section intitulée « Les produits »

Chaque produit est un dossier d’apps/, démarré par le SDK dans le navigateur (startWebApplication) et sur le bureau (startDesktopApplication, avec @fdw/editor-electron) : son profil, ses plugins, ses modèles d’exemple, les mêmes des deux côtés (src/product.ts). Un produit ne contient pas de fonctionnalité : ce qu’il montre vit dans les packages partagés (le profil dans editor-ui, les plugins dans editor/plugins/, le moteur dans engine/), pour que les démos, la documentation et les autres produits montrent le même code.

Produit Phase Web (port) Bureau
viewer P27 npx nx dev viewer (4310) npx nx run viewer:desktop
review P28 npx nx dev review (4311) npx nx run review:desktop
material-editor P29 npx nx dev material-editor (4312) npx nx run material-editor:desktop
game-editor P20 npx nx dev game-editor (4313) npx nx run game-editor:desktop
simulation P31 npx nx dev simulation (4314) npx nx run simulation:desktop

npx nx build <produit> le construit dans apps/<produit>/dist, et npx nx preview <produit> sert ce build. Le viewer et la revue ouvrent un modèle d’exemple au démarrage (roller.step), la simulation un résultat d’exemple (cantilever.vtu.series) ; ?open=<url> en ouvre un autre, et les autres options de lancement du SDK s’appliquent (?backend=webgl2, ?view=, ?docks=, ?embed).

Sur le bureau, le moteur tourne en natif (Vulkan, Direct3D 12 sur demande, Dawn en repli) dans un viewport placé sur la page ; le premier lancement installe la chaîne Electron partagée (tools/electron) et construit les addons natifs. desktop-build le construit dans apps/<produit>/desktop/out, desktop-preview lance ce build (le modèle d’exemple ne s’ouvre que depuis le serveur de dev : une page file: ne peut pas le récupérer), typecheck-desktop vérifie ses processus. Un plugin Nx local donne ces cibles à chaque produit qui a un desktop/electron.vite.config.ts (tools/apps/nx-desktop.mjs).

  • Un nouveau produit copie l’un d’eux : un package.json (privé, @fdw-engine/<produit>), un project.json (scope:apps, type:app), index.html et popout.html, son src/ et son vite.config.mts ; puis npm install et npx nx sync. Son nom Nx ne doit pas être celui d’un package (review, pas design-review).
  • Une fonctionnalité dont il a besoin va d’abord dans son domaine (un panneau dans un plugin d’editor/plugins/, une commande dans editor-ui) ; le produit ne fait que l’assembler. Ses plugins privés, dans apps/<produit>/plugins/, sont l’exception : ce qu’aucun autre produit ne montrera.
  • Un produit n’importe jamais un autre produit, ni les labs : ce que deux produits partagent descend dans editor/ ou dans le domaine qui le possède.
  • Sur le bureau, ses points d’entrée tiennent en une ligne chacun : ce qui change d’un produit à l’autre est dans src/product.ts, le reste dans @fdw/editor-electron. Lancé depuis un terminal des extensions de VS Code, retirez ELECTRON_RUN_AS_NODE : Electron démarrerait comme Node.

Ajouter un package

Section intitulée « Ajouter un package »
  1. Choisissez son domaine avec les deux questions ci-dessus, et son dossier : <domaine>/<nom>. Son nom dit son domaine : engine-… dans le moteur, editor-plugin-… pour un plugin de l’éditeur.
  2. Copiez un package du même domaine, comme engine/engine-input : package.json (nom @fdw/<nom>, exports vers ./src/index.ts), project.json, les tsconfig, vitest.config.mts, README.md.
  3. Taguez-le dans project.json : scope:<domaine>, runtime:, type:lib (ou type:plugin).
  4. Déclarez-le : son chemin dans tsconfig.base.json, sa description et son champ fdw dans package.json (L’architecture des packages).
  5. Installez et vérifiez :

Un nouveau dossier qui contient des projets (engine/plugins/, un produit d’apps/) s’ajoute aux workspaces du package.json de la racine et à projectParents dans tools/repo/layout.mjs.

Déplacer un package

Section intitulée « Déplacer un package »

tools/repo/move.mjs déplace des dossiers et réécrit les chemins qui pointent dedans : les chemins relatifs des configurations et des pages, et les chemins depuis la racine (engine/engine-core) dans les workflows, les scripts et la documentation. Les noms npm et les noms des projets Nx ne changent pas, donc aucun import non plus.

Changez ensuite son tag scope: s’il change de domaine, et relisez le diff : l’outil ne réécrit un chemin relatif que s’il pointe vers quelque chose qui existe.
