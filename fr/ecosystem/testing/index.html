Tests

Les tests utilisent Vitest. npx nx run-many -t test les exécute tous ; npx nx test <project> un seul projet ; npx nx run-many -t test-unit les seuls tests unitaires (voir Intégration continue pour les autres familles).

Tests unitaires

Section intitulée « Tests unitaires »

À côté du code, sous la forme src/**/*.spec.ts. Ils n’ont besoin d’aucun GPU :

  • engine-shader : des graphes construits, validés et compilés, vérifiés sur l’IR (instructions, étages, layout) ou sur les diagnostics.
  • engine-core : le renderer et le render graph sur un faux backend (src/testing/fakeBackend.ts), qui enregistre les ressources créées et les commandes encodées : ce qui est dessiné, dans quel ordre, avec quels buffers.
  • Générateurs de code : le code généré, sur de petits programmes.

La suite de rendu

Section intitulée « La suite de rendu »

tests/rendering rend les mêmes scènes sur chaque backend, à travers tout le moteur, dans des surfaces hors écran, et compare les pixels. Une fonctionnalité qui change ce qui est dessiné ajoute un test à src/suite.ts : il s’exécute alors sur tous les backends à la fois.

Fichier Backend Nécessite
dawn.spec.ts WebGPU sur Dawn, dans Node ; puis chaque programme de la suite, en HLSL et en GLSL ES le paquet webgpu (installé) ; le SDK Vulkan (DXC, spirv-val, spirv-cross, glslangValidator) pour les programmes
webgl2.browser.spec.ts WebGL2, dans Chromium headless npx playwright install chromium-headless-shell
vulkan.spec.ts Vulkan, avec la couche de validation le SDK Vulkan, et l’addon compilé

Sans le SDK, les tests Vulkan, HLSL et GLSL sont ignorés, pas en échec — sauf s’ils sont requis (voir Intégration continue). Sur Vulkan, un test échoue si la couche de validation signale quoi que ce soit. dawn.spec.ts enregistre les programmes compilés par la suite sur Dawn, puis (programs.ts, autant de programmes à la fois que de cœurs) :

  • compile chacun d’eux en HLSL avec DXC, valide le SPIR-V avec spirv-val, et compare les offsets des uniforms du layout avec la réflexion de spirv-cross ;
  • les génère en GLSL ES 3.00 (les étapes de calcul comme les dessins qui les émulent en WebGL2), puis les valide et les lie avec glslangValidator, plus strict que les compilateurs des navigateurs.

Les tests de pixels vérifient des valeurs exactes là où le GPU les calcule exactement (effacements, couleurs non éclairées), et des intervalles ailleurs (bords, filtrage) : les GPU arrondissent différemment.

Les paquets natifs

Section intitulée « Les paquets natifs »

engine-native et engine-vulkan testent leur partie TypeScript avec des addons mock, et leur partie native sur le vrai GPU lorsque les addons sont compilés. Leurs cibles (test-native, test-vulkan, test-d3d12) dépendent de build-native, et leurs entrées incluent VULKAN_SDK, VK_DRIVER_FILES, FDW_REQUIRE_SUITES et l’OS : Nx les relance quand ils changent.

Benchmarks

Section intitulée « Benchmarks »

Les fichiers *.bench.ts mesurent le coût CPU du renderer, du render graph, de la scène, de l’ECS, de la géométrie et du compilateur de shaders, sur le faux backend : npx vitest bench dans un paquet. Lancez-les avant et après une modification sur un chemin critique :

Sur chaque pull request, le workflow Benchmarks fait de même dans la CI : la modification et sa base mesurées dans le même job, comparées dans le résumé de l’exécution. Un benchmark est marqué plus lent ou plus rapide au-delà de 20 % et au-delà des marges d’erreur des deux mesures. Les runners sont partagés et bruités : le workflow n’échoue jamais, le tableau est un indice pour regarder de plus près.

Intégration continue

Section intitulée « Intégration continue »

Chaque pull request passe par GitHub Actions (.github/workflows/), et doit être verte pour être fusionnée dans main. Les vérifications sont découpées en familles de validation : chacune est une cible Nx lançable sur votre poste, et un job avec son environnement, son timeout et ses rapports :

Famille Cible Nx Tourne sur Ce qu’elle teste
Static — Linux Le format, typecheck et lint ; les tests de tools/ci
Unit test-unit Linux Les tests dans Node, sans GPU, navigateur, SDK ni addon
Browser test-browser Linux, Windows Les tests dans Chromium (engine-audio-web, editor-web)
WebGL2 test-webgl2 Linux, Windows La suite de rendu en WebGL2, dans Chromium sur SwiftShader
WebGPU test-webgpu Linux, Windows Dawn dans Node ; les programmes de la suite en HLSL et GLSL ES
Vulkan test-vulkan Linux, Windows engine-vulkan, la suite de rendu sur lavapipe
Direct3D 12 test-d3d12 Windows engine-d3d12, la suite de rendu sur WARP
Native test-native Linux, Windows L’addon d’engine-native, ses fenêtres, les paquets *-native
Editor test-editor Linux L’éditeur de bureau, de bout en bout, dans Electron
SDK package test-package Linux Le tutoriel web du SDK, construit hors du dépôt depuis les archives npm
SDK desktop package test-desktop-package Linux Le tutoriel desktop du SDK, construit, empaqueté et démarré hors du dépôt, sur lavapipe

tools/ci/select.mjs les choisit : sur une pull request, les projets que le changement affecte (nx show projects --affected) et qui ont la cible d’une famille ; tout quand un fichier global change (package-lock.json, nx.json, tsconfig*.json, tools/native/, tools/ci/, tools/sdk/, le workflow) ; tout à chaque push sur main. Un changement d’engine-webgl2 lance WebGL2, pas Vulkan ; un plugin de l’éditeur ne lance aucune suite de rendu. La règle de main n’exige qu’un statut, CI Required, qui vérifie que chaque famille sélectionnée a réussi et que les autres ont été sautées. Build the documentation reste à part (plus bas).

Les runners n’ont pas de GPU : Vulkan tourne sur lavapipe (le Vulkan logiciel de Mesa), Direct3D 12 sur WARP, WebGL2 dans Chromium sur SwiftShader, les fenêtres dans un écran virtuel (Xvfb). Chaque job de famille publie un artefact <famille>-<os> : le rapport JUnit des tests, les versions de l’environnement, les logs des compilations natives ; un job en échec dit dans son résumé s’il a échoué à l’installation, à la compilation ou aux tests.

Sur un poste, une suite dont le GPU, le SDK, l’addon ou l’écran manque est ignorée. En CI, FDW_REQUIRE_SUITES liste les suites qui doivent tourner (vulkan, dawn,hlsl,glsl, native,window…) : une suite absente échoue au lieu de passer en silence. Une nouvelle suite de ce genre appelle canRun(name, ready, reason) de @fdw/engine-backend/testing.

Où va un test

Section intitulée « Où va un test »
  • Un test unitaire (*.spec.ts) n’ouvre ni navigateur, ni adaptateur GPU, ni addon. Il tourne dans test-unit.
  • Un test qui a besoin de Dawn ou d’un GPU, dans un paquet qui a aussi des tests unitaires, se nomme *.gpu.spec.ts (engine-webgpu) ; un test dans Chromium, *.browser.spec.ts ; un test qui a besoin d’un addon, *.native.spec.ts.
  • Un nouveau paquet porte les tags scope: (engine, editor, viewer, shared, docs, demo, testing, tooling), runtime: (universal, web, native), type: (lib, plugin, app, test), et backend: s’il en implémente un ; ses dépendances dans son package.json : elles font le graphe que lit la sélection.

Les règles

Section intitulée « Les règles »
  • Aucun retry, aucun saut silencieux : une suite qui ne peut pas tourner échoue. Un job relancé à la main est noté dans la pull request (le job, la cause supposée).
  • Pas de timeout allongé pour faire passer un test lent : on le mesure (le rapport JUnit, le budget de durée), on corrige la cause, ou on déplace le test dans sa famille.
  • Le budget de durée compare chaque test à la médiane de ses cinq dernières durées sur main, pour sa famille et son OS : les plus lents sont listés dans le résumé du job, en avertissements. Il ne fait pas échouer la pull request : les runners sont partagés et bruyants.
  • Une ressource externe (un binaire, un SDK, un modèle) vient d’un cache ou d’une release du dépôt, jamais d’un téléchargement libre pendant un test.
  • Une nouvelle validation est d’abord une cible Nx lançable sur un poste, puis une famille dans tools/ci/families.mjs, jamais une condition sur des chemins dans le YAML. Un changement de .github/workflows/, tools/ci/, nx.json ou des tags met à jour le design de la CI.
  • node tools/ci/health.mjs donne le taux d’échec et la durée médiane de chaque job sur les 50 derniers runs de main.

Les images de référence des exemples

Section intitulée « Les images de référence des exemples »

Chaque exemple interactif de la documentation est rendu dans Chromium headless, sur WebGL2 et sur WebGPU, tous deux sur SwiftShader, et son canvas comparé à une image de référence (apps/docs/tests/screenshots/) :

Les exemples s’exécutent avec leur horloge arrêtée et s’arrêtent après quelques frames (?time=1.5&frames=10) : l’image est la même à chaque exécution.

Quand une modification change ce qu’un exemple dessine, mettez à jour ses références, regardez-les, et commitez-les avec la modification. Si la CI rend un peu différemment de votre machine, lancez à la main le workflow Documentation avec update-screenshots : il rend les références sur la machine de la CI et les fournit sous forme d’artefact. Quand une comparaison échoue, le rapport avec les images de la différence est un artefact de l’exécution.

Avant de soumettre

Section intitulée « Avant de soumettre »

Travaillez sur une branche, et ouvrez une pull request : main ne reçoit que des pull requests squashées.

Un npm install avec une autre version de Node écrit le lockfile autrement : la CI échoue alors à son installation.
