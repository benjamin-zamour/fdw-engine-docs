Étape 1 : le labyrinthe

La première étape construit le monde du jeu : un labyrinthe de 48 × 48 cellules, généré à partir d’une graine, environ 4700 nœuds. Une caméra le survole, et une vue de dessus dans le coin montre ce que la caméra retient : seul cela est dessiné.

…

Cliquez sur le labyrinthe, puis : W A S D ou les flèches pour vous déplacer, Q et E pour tourner, la molette pour monter ou descendre, Maj pour aller plus vite. Avec une manette : le stick gauche pour vous déplacer (enfoncé pour aller plus vite), les bumpers pour tourner, la croix directionnelle, haut et bas, pour monter ou descendre.

1. Générer le labyrinthe

Section intitulée « 1. Générer le labyrinthe »

Un labyrinthe est une grille de cellules, chacune avec quatre murs. Le générateur parcourt la grille en profondeur d’abord — le « recursive backtracker » : depuis une cellule, il va vers une voisine au hasard pas encore visitée et ouvre le mur qui les sépare ; lorsqu’il ne reste aucune voisine, il revient en arrière. Chaque cellule est alors atteignable, par un seul chemin.

Les murs sont des bits d’un Uint8Array : compacts, et rapides à tester. Le générateur aléatoire a une graine (seededRandom(), un mulberry32) : la même graine donne le même labyrinthe, ce qui compte pour les tests et pour partager un niveau.

2. Construire le niveau

Section intitulée « 2. Construire le niveau »

Chaque cellule devient une dalle de sol ; chaque côté fermé, un mur. Les deux sont des cubes, mis à l’échelle :

Trois choix comptent ici :

  • Nœuds statiques. Le niveau ne bouge jamais : static: true indique à la scène de calculer ces nœuds une seule fois, et de les indexer tous d’un coup dans un index spatial qui leur est propre (un octree construit de haut en bas), à la première frame.
  • Occluders. Les murs cachent ce qui se trouve derrière eux : occluder: true les marque. Vu de dessus, un labyrinthe cache peu de chose : le jeu le dessine sans l’occlusion culling, qui est rentable au niveau des rues.
  • Groupes. floor et walls sont des nœuds sans mesh : ils organisent la hiérarchie (level.walls.children liste les murs) sans rien coûter au dessin.

3. Le clavier, la souris et la manette

Section intitulée « 3. Le clavier, la souris et la manette »

Le jeu lit ses entrées avec @fdw/engine-input. L’origine des événements est donnée par la page ou l’application — un WebInputSource sur le canvas, un NativeInputSource sur une fenêtre native — et le jeu construit un Input dessus :

Le code du jeu ne lit pas de touches : il lit des actions, déclarées une fois avec leurs liaisons — le clavier, et la manette :

  • KeyW est une position sur le clavier, pas une lettre : sur un clavier AZERTY, la même touche est Z, et le jeu se joue avec ZQSD sans configuration.
  • move est un vecteur, x vers la droite et y vers l’avant, de longueur 0 à 1 : quatre touches, ou un stick. La liaison la plus forte l’emporte.

Chaque frame commence par input.update() : il applique les événements reçus depuis la frame précédente et lit les manettes, puis l’état reste le même pendant la frame. Se déplacer tant qu’une touche est enfoncée revient alors à multiplier une vitesse par la durée de la frame.

Voir Entrées pour l’ensemble de l’API.

4. La caméra

Section intitulée « 4. La caméra »

La caméra est un nœud de la scène : setCamera(camera) lui fait suivre le nœud, en regardant le long de son axe −z. La caméra libre déplace le nœud :

La rotation est un lacet (autour de la verticale) puis un tangage (vers le bas) : le produit de deux quaternions. La vitesse croît avec la hauteur, de sorte que le labyrinthe défile au même rythme quel que soit le zoom.

5. Le rendu : la vue principale

Section intitulée « 5. Le rendu : la vue principale »

renderer.render({ source: scene, … }) suffirait pour une vue. La vue de dessus en demande une seconde dans la même frame, donc la frame est un render graph :

Le renderer demande à la scène ce qui se trouve dans le frustum de la caméra : sur les 4700 nœuds, quelques centaines. La ligne sous le canvas indique combien, et combien sont dessinés dans la shadow map du soleil — seulement ceux dont les ombres peuvent tomber dans la vue.

6. La vue de dessus

Section intitulée « 6. La vue de dessus »

La vue de dessus dessine le niveau vu d’en haut, avec une caméra orthographique, mais seulement les nœuds que la caméra principale a retenus. La scène mémorise, sur chaque nœud, la dernière requête de caméra qui l’a gardé (NodeState.lastVisible) ; la vue de dessus donne au renderer une source qui filtre selon cette valeur :

La vue de dessus est dessinée dans une petite texture, puis par-dessus la vue principale par une passe plein écran qui ne couvre qu’un coin de l’écran : un matériau qui lit la texture dans un rectangle, transparent ailleurs, mélangé (blend: true) :

Le repère de la caméra est une sphère sur une couche qui lui est propre (TopViewLayer) : la vue principale, dont les couches sont ~TopViewLayer, ne la voit pas.

Ce que nous avons

Section intitulée « Ce que nous avons »
  • Un monde de milliers de nœuds statiques, indexés une seule fois, et dessinés seulement là où regarde la caméra.
  • Une frame composée de deux vues dans un render graph, assemblées par une passe plein écran mélangée.
  • Des entrées qui fonctionnent de la même façon dans une page, dans la démo et dans une fenêtre native.
