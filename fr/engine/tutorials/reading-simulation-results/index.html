Lire des résultats de simulation

Un solveur écrit ses résultats sur son propre maillage : des points et des cellules, des champs aux points ou dans les cellules, un fichier par pas de temps. Le lecteur de VTK les lit dans le modèle pivot, comme une extension que le cœur du pivot garde sans la lire : les résultats de @fdw/pivot-results. Ici, une poutre encastrée en acier dont la charge monte de 0 à 20 kN en 11 pas, un fichier .vtu par pas : chaque cellule dans la couleur de sa contrainte de von Mises, les valeurs d’un pas lues quand il s’affiche. À partir du pas 8, deux cellules de l’encastrement ont rompu : le fichier n’y a pas de valeur, elles gardent la couleur des valeurs absentes.

Le lecteur

Section intitulée « Le lecteur »

registerVtk enregistre le lecteur des .vtk, .vtu, .vtp et de leurs séries, .series et .pvd (le plugin fdw.vtk). Une série nomme d’autres fichiers : le résolveur les lit, à côté d’elle.

VTK n’a pas d’unités. Sans frame, le lecteur suppose des mètres et Z vers le haut, et le dit dans le rapport ; sans units, les champs n’ont pas d’unité, et le rapport dit lesquels. Une unité n’est jamais inventée ni convertie.

Ce que devient un fichier

Section intitulée « Ce que devient un fichier »

resultSets trouve les résultats d’un modèle :

  • Le maillage de résultats est celui du solveur, tel que lu : ses points, ses cellules (leurs types et l’ordre de leurs points sont ceux de VTK, CellType), les numéros que le solveur leur a donnés quand le fichier les a (GlobalNodeId, GlobalElementId). Ce n’est pas le maillage affiché, et un nœud de l’arbre le nomme.
  • Un champ garde sa localisation : aux points, ou constant dans les cellules. Passer de l’une à l’autre changerait des valeurs ; c’est un choix à faire visiblement, jamais une lecture.
  • L’axe porte les pas : les temps d’une série, celui de TimeValue pour un fichier seul. Les cas de charge, les modes propres et les fréquences sont des axes aussi (axis: 'mode').

Les valeurs à la demande

Section intitulée « Les valeurs à la demande »

Le lecteur lit d’abord le maillage et la description des champs ; les valeurs d’un champ à un pas sont des ressources à part, deferred. Un FieldCache les lit quand on les demande, depuis le fichier de leur pas, et les garde dans un budget d’octets, les moins récemment utilisées évincées d’abord :

Deux demandes des mêmes valeurs les lisent une fois ; une demande s’annule par son signal sans arrêter la lecture pour les autres.

Les valeurs absentes

Section intitulée « Les valeurs absentes »

Une valeur que le fichier n’a pas est NaN, jamais interpolée : fieldRange les compte et les saute, l’échelle de couleurs leur donne sa couleur des valeurs absentes. Un pas dont le fichier n’a pas ce champ revient missing, avec la raison, et une ligne au rapport ; de même pour un pas dont le maillage n’est pas celui du premier pas.

L’afficher

Section intitulée « L’afficher »

resultSkin donne les faces extérieures des cellules, chacune avec ses propres sommets pour qu’une valeur constante dans une cellule le reste sur ses faces ; chaque triangle dit sa cellule, chaque sommet son point. L’exemple colore les sommets de chaque triangle par la valeur de sa cellule, avec l’échelle de couleurs et sa légende :

Les valeurs sont en pascals ; la légende montre des mégapascals, et le dit par son unité.

Ce qu’il dit

Section intitulée « Ce qu’il dit »

Un fichier qui n’est pas du VTK, ou un jeu de données que le lecteur ne lit pas (grilles structurées, multiblocs), échoue avec une PivotError. Une table de couleurs du fichier est une ligne lost : les palettes sont celles du viewer. En mode strict, les unités doivent être données.

La suite

Section intitulée « La suite »

Le profil de simulation du viewer s’appuie sur ceci : les contours sur le modèle, la déformée au facteur affiché, la barre de temps sur les pas, les sondes et leurs courbes.
