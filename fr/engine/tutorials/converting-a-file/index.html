Convertir un fichier

La conversion lit un fichier dans le modèle pivot et l’écrit dans un autre format, avec un seul rapport pour le lecteur, la validation et l’écrivain : ce qui n’est pas conservé est une ligne, jamais une perte silencieuse. glTF est le premier format branché, par @fdw/engine-gltf : son lecteur et son écrivain reprennent le code du chargeur du moteur. Ici, une fougère en .glb est convertie en .gltf, son .bin et ses images à côté ; les deux fichiers sont ensuite chargés par le pivot et affichés côte à côte : l’original à gauche, la conversion à droite.

Le plugin de glTF

Section intitulée « Le plugin de glTF »

registerGltf enregistre dans un registre du pivot un lecteur et un écrivain de .gltf et .glb (le plugin fdw.gltf, ses capacités pivot.reader et pivot.writer). Ses options sont celles du chargeur : les décodeurs d’EXT_meshopt_compression et de KHR_draco_mesh_compression, des extensions maison, les bornes de la mémoire qu’un fichier peut demander.

Convertir

Section intitulée « Convertir »

convert choisit le lecteur par le nom de la source, et l’écrivain par le nom demandé : .glb écrit un seul fichier binaire, .gltf un fichier JSON et son .bin. embedTextures met les images dans le buffer, ou à côté du fichier (par défaut pour un .gltf).

Les fichiers à côté d’un .gltf (ses buffers, ses images) sont lus par le résolveur donné à convert : le lecteur lit les buffers, et laisse les images par leur URI, lues seulement quand un écrivain ou le moteur en a besoin.

Avec mode: 'strict', la première ligne qui n’est pas kept fait échouer la conversion par une PivotError, sa ligne dans error.entry.

Ce que glTF garde

Section intitulée « Ce que glTF garde »

Le lecteur fait d’un fichier glTF ce que le pivot porte :

  • Les nœuds, leur TRS ou leur matrice tels qu’écrits, la scène par défaut ; les nœuds d’EXT_mesh_gpu_instancing deviennent un prototype et une instance par transform. KHR_node_visibility cache un nœud.
  • Les meshes : tous les modes (bandes et éventails mis en listes), les morph targets, les attributs quantifiés tels quels ; une clé source par élément (nodes/3, meshes/0).
  • Les matériaux, en material graphs du moteur : le PBR de glTF, KHR_materials_unlit, KHR_materials_emissive_strength, KHR_texture_transform, et les matériaux en graph de FDW_scene, exacts.
  • Les textures : celles du fichier en octets, sans copie ; celles d’à côté par leur URI, pour le résolveur.
  • Les peaux, les animations, les caméras, les lumières (KHR_lights_punctual).
  • Les extras deviennent des propriétés (textes, nombres, booléens, listes de nombres) ; les extensions qu’il n’interprète pas sont gardées telles quelles dans celles de leurs objets, et réécrites.

L’écrivain dit ce que glTF ne peut pas porter :

Dans le pivot Dans glTF La ligne
Un graph qui n’est pas le PBR de glTF Dans FDW_scene, relu exact ; approché en PBR pour les autres outils degraded
Une instance de matériau Un matériau à part entière degraded
Les apparences de la CAO Des matériaux, un par couleur ; une primitive découpée selon ses faces degraded
Une instance par référence Une copie des nœuds de son prototype, les meshes partagés degraded
Un autre repère (millimètres, Z vers le haut) Un nœud racine qui le convertit kept
Les unités et les dates des propriétés extras pour les autres outils, exactes dans FDW_pivot aucune
Les faces d’un B-rep, l’historique Rien lost
Une extension de glTF gardée telle que lue Réécrite, ses indices non renumérotés degraded

Un fichier glTF lu puis réécrit ne perd rien : ses seules lignes sont celles des extensions réécrites, et des instances d’EXT_mesh_gpu_instancing, écrites en copies.

Un seul chemin vers le GPU

Section intitulée « Un seul chemin vers le GPU »

Avec installPivot, le store charge .gltf et .glb par le pivot : le lecteur, la validation, puis l’adaptateur (Le pivot dans le moteur). Le modèle a la structure de celui du chargeur de glTF (installGltf) : les mêmes nœuds, meshes, peaux et animations ; le lien #pivot en garde la structure, et exportScene réécrit la scène en glTF.

L’exemple convertit avec storeResolver(resources), qui lit les fichiers du store, et met les fichiers écrits dans une MemorySource, d’où le store charge la fougère convertie.
