Écrire un lecteur

La conversion lit chaque format dans un même modèle en mémoire, le modèle pivot, et l’écrit dans n’importe quel autre. Un format est un plugin : un lecteur (des octets en entrée, un modèle en sortie), un écrivain (un modèle en entrée, des fichiers en sortie), et un manifeste qui les déclare. Ici, STL en ASCII, le format de l’impression 3D : une liste de triangles, rien d’autre.

Le code de cette page est testé avec le package (tutorial.spec.ts d’@fdw/pivot).

Le lecteur

Section intitulée « Le lecteur »

Un lecteur construit un modèle avec un PivotBuilder : des ressources (ici un mesh), puis les nœuds qui les placent.

Trois choses à remarquer :

  • Le repère est déclaré, pas converti. Le lecteur dit ce qu’est le fichier (des millimètres, Z en haut) ; l’adaptateur vers le moteur ou l’écrivain d’un autre format convertit, avec frameMatrix.
  • Ce que le lecteur suppose est une ligne du rapport. Les unités d’un fichier STL sont une supposition : la ligne le dit. En mode strict, cette ligne fait échouer la lecture ; en mode permissif, celui par défaut, elle est rapportée.
  • Les identifiants sont aléatoires ; la sourceKey est l’identité de l’élément dans son fichier, ce dont un viewer se sert pour le retrouver à la lecture suivante.

Un fichier qui n’est pas du STL du tout est une erreur : le lecteur lève une exception.

L’écrivain

Section intitulée « L’écrivain »

Un écrivain parcourt le modèle et écrit ses fichiers. STL n’a qu’un solide, sans hiérarchie ni matériaux : l’écrivain applique la matrice monde de chaque occurrence (une pièce placée deux fois est écrite deux fois), et rapporte ce qu’il perd.

L’écrivain reçoit un modèle déjà validé : chaque référence se résout, l’arbre n’a pas de cycle. Il n’a pas à les vérifier de nouveau.

Le manifeste et le registre

Section intitulée « Le manifeste et le registre »

Le plugin déclare ses capacités en JSON, lu sans son code : les contrats pivot.reader et pivot.writer, leurs formats, leurs extensions (en minuscules, avec leur point) et ce qu’ils portent.

read choisit le lecteur par l’extension du fichier, charge son code à son premier usage, et valide le modèle qu’il donne. write valide, puis écrit ; convert lit avec un plugin et écrit avec un autre, dans un seul rapport :

Chaque ligne connaît son étape : l’identifiant du lecteur ou de l’écrivain, ou validate. Avec mode: 'strict', la première perte lève une PivotError avec sa ligne, et rien n’est écrit.

Pour aller plus loin

Section intitulée « Pour aller plus loin »
  • Des textures à côté du fichier : donnez-les en source uri ; l’application passe un resolver à read, et textureBytes les lit quand on en a besoin.
  • Les gros fichiers : un lecteur qui déclare onDemand: true donne ses ressources lourdes en deferred et implémente readResource ; le viewer lit chaque pièce quand elle devient visible.
  • Les données du format que le pivot n’interprète pas vont dans les extensions des nœuds et des ressources, par espace de noms : un écrivain du même format les relit.
