Ressources

Le système de ressources charge ce qu’une application lit dans des fichiers : images, modèles, sons (L’audio), ses propres données. Il est découpé comme l’entrée :

Paquet Contenu
@fdw/engine-resources Le store, les poignées, les scopes, les chargeurs, les sources (HttpSource, MemorySource, DataUriSource, ArchiveSource)
@fdw/engine-resources-web Le décodage des images par le navigateur, les fichiers choisis ou déposés (FileSource), le rechargement à chaud par Vite, les workers
@fdw/engine-resources-native Les fichiers (FileSource, withFileWatch), le décodage stb_image dans l’addon, les worker_threads
@fdw/engine-assets Images, textures, meshes, matériaux, modèles ; instantiate() dans une scène
@fdw/engine-gltf, @fdw/engine-obj, @fdw/engine-ktx2 Les formats : des octets en entrée, des données CPU en sortie

Le cœur ne connaît ni le GPU ni la scène : le même store charge les modèles d’un niveau et les réglages de ses ennemis.

Le store

Section intitulée « Le store »

Un store par moteur, créé avec l’application et passé explicitement : pas de singleton, donc les tests, deux moteurs et un éditeur à plusieurs scènes restent séparés.

Une ressource est un type et une URI. load() rend une poignée tout de suite ; le chargement continue en arrière-plan :

  • Deux load() du même type, de la même URI et des mêmes options partagent une entrée et une lecture. resources.load(TextureType, 'a.png') et resources.load(TextureType, 'http:./a.png') sont la même ressource.
  • handle.value est la valeur courante — pendant un rechargement, la précédente — et handle.require() la valeur ou une erreur.
  • handle.version augmente à chaque changement : un signal à suivre.
  • priority: 'high' | 'normal' | 'low' ordonne la file ; signal annule de l’extérieur.

URI et sources

Section intitulée « URI et sources »

Une URI est schéma:chemin#fragment. Sans schéma, celui par défaut. Les sources sont montées sous un schéma comme les lecteurs d’un système de fichiers :

Plusieurs sources sous un même schéma sont essayées par priorité jusqu’à ce que l’une ait le fichier : un dossier de correctifs au-dessus de l’archive du jeu.

Source Paquet Lit
HttpSource cœur fetch, avec progression, annulation, stat par ETag
MemorySource cœur Des fichiers en mémoire (set() prévient les observateurs) : tests, données générées
DataUriSource cœur Les URI data:, en base64 ou non
ArchiveSource cœur Les entrées d’un zip lu depuis une autre source, à la demande
CatalogSource cœur Des identifiants stables sur les chemins d’une autre source
FileSource -web Les File d’un <input> ou d’un glisser-déposer, dossiers compris
DirectorySource -web Un dossier choisi par la File System Access API ; écrit aussi
FileSource -native Les fichiers sous un dossier racine ; écrit aussi

Le fragment nomme une sous-ressource : les meshes et matériaux d’un modèle sont oak.glb#mesh/Trunk/0 et oak.glb#material/Bark, ses images intégrées oak.glb#image/0. Ces identifiants sont stables : un éditeur les enregistrera dans ses scènes.

Les projets et le catalogue

Section intitulée « Les projets et le catalogue »

Une application qui édite ses assets (un éditeur, une bibliothèque de matériaux) travaille dans un projet : un dossier avec son manifeste, fdw-project.json, et à côté de chaque source ses métadonnées, oak.glb.meta, qui lui donnent un GUID. Le catalogue est dérivé des métadonnées et monté comme une source : asset:<guid> lit la source où qu’elle soit, et une scène qui y fait référence survit à un déplacement.

Le dossier est une source qui écrit aussi : FileSource en Node, DirectorySource sur le web, MemoryFolder dans les tests. Le tutoriel Les projets et le catalogue montre les métadonnées, les déplacements, les doublons et les références des scènes.

Chargeurs et types

Section intitulée « Chargeurs et types »

Un type est un jeton typé ; un chargeur transforme les octets d’une URI en valeur :

Le contexte donne au chargeur :

  • bytes() et text() : le contenu, lu une fois ;
  • resolve(relative) : un chemin relatif à la ressource (un glTF et ses textures) ;
  • use(type, uri, options) : une dépendance. Sa progression compte dans celle du parent, elle est libérée avec lui, et son rechargement met le parent à jour. Un cycle est refusé avec son chemin ;
  • provide(type, id, value) : une sous-ressource uri#id ;
  • service(key) : un service du store (le backend de rendu) ;
  • signal : déclenché quand plus personne n’attend le résultat.

Un chargeur peut aussi donner update(current, next) pour mettre une valeur à jour en place au rechargement, dispose(value) pour la libérer, sizeOf(value) pour le budget du cache, cacheKey(options), et sniff(head) pour reconnaître son format quand l’extension ment. Plusieurs chargeurs d’un même type sont choisis par extension, puis par sniff.

Durées de vie

Section intitulée « Durées de vie »

Chaque poignée compte. Une entrée vit tant qu’elle a des poignées ou des dépendants :

  • handle.release() est idempotent ; using handle = resources.load(…) libère à la fin du bloc.
  • La dernière poignée libérée pendant le chargement l’annule, avec les dépendances que personne d’autre n’utilise.
  • Une entrée sans poignée reste en cache, sa valeur gardée : revenir dans un niveau qu’on vient de quitter est immédiat. Les moins récemment utilisées sont libérées quand les inutilisées dépassent le budget, ou par trim(). trim(0) les libère toutes.
  • La libération appelle le dispose du chargeur : les textures GPU y sont détruites, les buffers d’un mesh libérés dans tous les renderers.
  • Une poignée oubliée sans release() est signalée quand elle est collectée : un filet, jamais le mécanisme.

Progression et erreurs

Section intitulée « Progression et erreurs »

La progression d’une ressource comprend celle de ses dépendances, en octets quand les tailles sont connues.

Les échecs sont des ResourceError avec un code — not-found, decode, unsupported, aborted, dependency, io — et la chaîne des URI : oak.glb → bark.png. Une ressource en échec est rechargée par le load() suivant. Une texture de matériau qui échoue affiche un damier magenta par défaut (installAssets(store, { onMissing: 'fail' }) fait échouer le matériau).

Le rechargement à chaud

Section intitulée « Le rechargement à chaud »

Les sources qui savent surveiller (FileSource et withFileWatch dans Node, MemorySource, une source enveloppée par withChangeChannel ou withPolling sur le web) disent au store quels fichiers ont changé. Le store les recharge ; l’ancienne valeur reste utilisée jusqu’à ce que la nouvelle soit complète, et un échec la garde, avec l’erreur sur handle.error.

update(budgetMs) échange les valeurs rechargées, dans un budget de temps. Avec l’ordonnanceur de la scène, addResourceSystem(scheduler, resources) l’appelle au début de chaque image.

  • Un mesh de même disposition reçoit ses nouveaux sommets en place, un matériau de même graphe ses nouvelles valeurs : les nœuds qui les dessinent voient le changement sans rien faire.
  • Sinon la valeur est remplacée, et ses dépendants suivent : un matériau dont la texture a changé prend la nouvelle.
  • resources.reload(uri) recharge explicitement.

Les ressources graphiques

Section intitulée « Les ressources graphiques »

installAssets enregistre les images, textures, meshes, matériaux et modèles, sur deux niveaux : les chargeurs de formats produisent des données CPU (ImageAsset, MeshData, PbrMaterialData, ModelData), les réalisations en font des objets du moteur (Texture, Mesh, Material, Model). Les formats se testent sans GPU, et un changement de backend réalise tout à nouveau sans relire un fichier :

Type Valeur
TextureType Une GpuTexture et son sampler partagé ; options colorSpace ('srgb' par défaut, 'linear' pour les données), mips, sampler
MeshType Un Mesh du moteur (une sous-ressource d’un modèle)
MaterialType Un Material : un graphe par jeu de caractéristiques (quelles textures, quels jeux d’uv), les facteurs en uniforms
ModelType Un Model : sa hiérarchie, et les meshes et matériaux de ses primitives

L’espace colorimétrique est un choix de la texture, pas du fichier : une couleur de base est sRGB, une carte de normales linéaire, et une même image peut servir aux deux.

Les images sont décodées par des codecs : bitmapCodec sur createImageBitmap dans le navigateur (couleurs et alpha laissés tels quels, ce dont une carte de normales a besoin), pixelCodec sur stb_image dans Node (PNG, JPEG, TGA, BMP, GIF, HDR en rgba16float), ktx2Codec pour les fichiers KTX2 et leurs formats compressés.

Avec keepCpuData: 'never' (par défaut) les pixels sont libérés une fois sur le GPU ; un changement de backend relit les fichiers. 'always' les garde, pour un éditeur.

Des modèles dans une scène

Section intitulée « Des modèles dans une scène »

instantiate crée les nœuds du modèle sous un nouveau nœud, et rend une ModelInstance (root, nodes, rebuild(), dispose()). Les instances partagent les meshes et matériaux du modèle : dix arbres sont dessinés en un appel par primitive grâce à l’instancing. Avec une poignée, une instance garde le modèle en vie jusqu’à son dispose().

glTF, OBJ, KTX2

Section intitulée « glTF, OBJ, KTX2 »
  • glTF 2.0 (.gltf, .glb) : meshes (un par primitive), matériaux metallic / roughness, hiérarchie, caméras, peaux et animations (lues, pour l’animation d’une phase suivante), et les extensions KHR_materials_unlit, KHR_texture_transform, KHR_materials_emissive_strength, KHR_mesh_quantization, KHR_lights_punctual, KHR_texture_basisu. EXT_meshopt_compression et KHR_draco_mesh_compression utilisent les décodeurs que donne l’application : installGltf(resources, { meshopt: MeshoptDecoder }), ou décodent dans des workers (plus bas). Le moteur ne les embarque pas.
  • OBJ et ses fichiers MTL : un nœud par objet ou groupe, des matériaux Phong avec leurs cartes.
  • KTX2 : niveaux de mip, cubes, tableaux, formats BC / ETC2 / ASTC quand le backend sait les échantillonner (capabilities.compressedFormats), Basis Universal par un transcodeur donné par l’application.

Les limites d’allocation de glTF

Section intitulée « Les limites d’allocation de glTF »

Un accessor déclare son nombre d’éléments ; sans buffer view (des zéros, puis des valeurs sparse), rien dans le fichier ne porte ses octets : quelques octets de JSON pourraient demander des gigaoctets. Le chargeur vérifie chaque tableau avant de l’allouer :

Option Variable d’environnement Défaut Borne
maxAccessorBytes FDW_GLTF_MAX_ACCESSOR_BYTES 256 Mio un accessor (et une buffer view meshopt)
maxTotalAccessorBytes FDW_GLTF_MAX_TOTAL_ACCESSOR_BYTES 2 Gio tous les accessors d’un fichier

256 Mio contiennent 22 millions de VEC3 flottants ou 67 millions d’indices uint32 : les vrais maillages de dizaines de millions de sommets se chargent, un fichier hostile échoue avec une erreur qui nomme la limite. Les options d’installGltf passent d’abord ; les variables sont lues là où il y a un process (Node, Electron), en octets ou avec une unité (512MB, 1GiB). 0 retire une borne :

Le décodage dans des workers

Section intitulée « Le décodage dans des workers »

Le décodage lourd peut tourner dans les workers d’un pool plutôt que sur le thread principal. Un seul script de worker sert tous les décodeurs, et le même pool est donné à chacun :

Format Dans les workers Sur le thread principal
Images (web) createImageBitmap L’ImageBitmap reçue
glTF La géométrie de chaque primitive (accesseurs, valeurs creuses, attributs quantifiés, bandes et éventails, normales plates), meshopt, Draco Le JSON et le conteneur GLB, matériaux, hiérarchie, peaux, animations
KTX2 La décompression des niveaux (zlib, zstd), le transcodage Basis Universal Les en-têtes du conteneur
  • Sans workers, tout est décodé sur le thread principal par les décodeurs des options (meshopt, draco, transcoder, zstd), comme avant.
  • Avec workers, les décodeurs vivent dans le script du worker : draco3d et basis_transcoder sont des modules WASM que l’application y charge, et ceux des options ne servent pas. Un fichier qui demande un décodeur absent du script échoue en decode, en le nommant.
  • Ce qui est posté est une copie de sa plage du fichier, déplacée vers le worker (le fichier reste utilisable : une texture le transcode de nouveau pour un autre backend) ; les résultats reviennent déplacés, pas copiés. Un chargement annulé abandonne les résultats de ses tâches.
  • @fdw/engine-gltf/worker et @fdw/engine-ktx2/worker n’importent que les tâches, pas le moteur : le script du worker reste petit.
  • createLocalPool(tasks) exécute les tâches sur le thread appelant, clonées comme entre deux threads : pour les tests, ou une plateforme sans workers.
