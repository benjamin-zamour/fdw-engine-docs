L'état de visualisation

@fdw/view-state garde comment un modèle est regardé : les éléments masqués, isolés, colorés ; les annotations (les mesures, et les types que déclarent les plugins : commentaires, sondes) ; les vues de caméra ; les sections. En mémoire, sans GPU ; le modèle n’est jamais modifié pour être regardé. Chaque application s’appuie dessus : le viewer de l’éditeur y garde sa visibilité et ses couleurs, les mesures et les sections y vivent.

Les références

Section intitulée « Les références »

L’état ne garde jamais les éléments eux-mêmes, absents quand il est relu : il les désigne par des références, { path, key }.

  • path : les identifiants depuis la racine, le chemin d’instance (les identifiants stables d’un niveau, ceux du pivot pour un modèle ouvert) ;
  • key : la clé source de l’élément (un identifiant FBX, l’indice d’un nœud glTF), préfixée par son modèle : ce qui reste d’une lecture du fichier à la suivante, quand les identifiants du pivot changent.

Une application trouve ses éléments par un ElementIndex : byPath, byKey, et refOf, la référence d’un élément. resolve(index) donne l’apparence, l’isolation et les ancres des annotations en éléments : par leurs identifiants, puis par leur clé source. Une référence trouvée par sa clé prend les nouveaux identifiants (la résolution suivante la trouve par eux) et un diagnostic le dit (source-key-fallback) ; une référence introuvable reste, avec un unresolved : l’utilisateur voit les deux.

Les annotations

Section intitulée « Les annotations »

Une annotation a un type, ses données, les éléments où elle est ancrée. Un type est déclaré par un plugin, qui écrit et lit ses données :

Les données sont vérifiées par un aller-retour par leur type à l’ajout : ce qui ne pourrait pas s’exporter est refusé tout de suite. Les types des plugins sont déclarés par la capacité view-state.annotation du manifeste commun (annotationTypesManifest, AnnotationTypes.registerPlugins) : leur code est chargé à la première lecture d’un état qui en contient. Une annotation d’un type que personne ne déclare est gardée telle que lue et réécrite inchangée, jamais montrée ; une que son type refuse est écartée ; les deux sont dites.

Les types que donne la plateforme : les mesures (measure.distance, measure.angle, measure.radius, Les mesures), les sondes, la palette de chaque grandeur et le temps (data.probe, data.color-scale, data.time, Palettes, temps et sondes).

Les sections et leurs limites

Section intitulée « Les sections et leurs limites »

Les sections (voir Les coupes) sont des objets de l’état : nommées, actives ou non, fermées ou ouvertes, avec leur apparence (le remplissage des tranches : une couleur, des hachures ou une texture ; le plan : sa couleur, son opacité de 0 à 1, sa bordure). Les limites sont celles du profil, jamais plus que ce que dessine le renderer ; un ajout qui les dépasse lève limit, et l’état reste inchangé.

L’explosion

Section intitulée « L’explosion »

Une vue éclatée est un déplacement des instances dans l’état, jamais dans le modèle (voir Éclater un modèle) : setExplosion({ mode, factor, spread, center, axis, offsets, traces }). Quatre modes : radial (les pièces s’éloignent d’un point, le centre du modèle par défaut), axial (le long d’un axe, le plus grand côté du modèle par défaut), levels (chaque assemblage s’éloigne du centre de son parent, puis ses pièces en lui), manual (le déplacement de chaque élément au facteur 1, par référence). factor va de 0, assemblé, à 1 ; spread met les distances à l’échelle. explosionOffsets(tree, explosion) donne le déplacement de chaque élément d’un arbre à bornes, le même dans toutes les applications ; les déplacements manuels sont des références, trouvées par resolve(index) comme les autres.

En JSON

Section intitulée « En JSON »

toJSON() écrit tout (format: 'fdw.view-state' ; version: 1, ou 2 avec une explosion, qu’un lecteur de la version 1 refuse plutôt que de la perdre) ; ViewState.read(document, { types }) ou state.load(document) le relit, avec ses diagnostics. Lire un autre format, ou une version ultérieure, lève format.

Dans des fichiers

Section intitulée « Dans des fichiers »

ViewStatePersistence écrit l’état dans des fichiers et le relit, par les exporteurs et les importeurs déclarés par des plugins (view-state.exporter, view-state.importer), avec un rapport en mode permissive ou strict. Le plugin par défaut écrit le fichier compagnon du modèle (bracket.glb.view.json), lisible et versionnable : voir Enregistrer l’état.

Dans l’éditeur, LevelDocument.saveViewState() et loadViewState() donnent l’état d’un niveau ; les nœuds d’un modèle rouvert sont retrouvés par leur clé source, et la console le dit.
