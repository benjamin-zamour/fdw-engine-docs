Backends et surfaces

Trois objets séparent une application de l’API graphique sur laquelle elle s’exécute.

Objet Rôle Interface (@fdw/engine-backend)
Engine Le périphérique : créé par init(), libéré par destroy() ; son state est un signal Engine
Surface La destination des frames : un canvas, une fenêtre, une texture. width, height, format, present() Surface
RenderBackend Ce qu’utilisent les renderers : fabriques de buffers, de textures et de pipelines, mathématiques, encodage des commandes RenderBackend, engine.backend

Le Renderer, les matériaux et le render graph ne voient que le RenderBackend et la Surface : le code écrit pour ces interfaces fonctionne partout.

Les backends

Section intitulée « Les backends »
Backend Package Engine Surfaces Shaders
WebGPU @fdw/engine-webgpu WebGpuEngine WebGpuSurface (canvas), WebGpuOffscreenSurface WGSL
WebGL2 @fdw/engine-webgl2 WebGl2Engine WebGl2CanvasSurface, WebGl2OffscreenSurface GLSL ES 3.00
Dawn @fdw/engine-native createDawnEngine() DawnWindowSurface, WebGpuOffscreenSurface WGSL
Vulkan @fdw/engine-vulkan VulkanEngine VulkanWindowSurface (@fdw/engine-native), VulkanOffscreenSurface HLSL, compilé en SPIR-V par DXC

Tous les backends passent la même suite de tests de rendu.

Surfaces hors écran

Section intitulée « Surfaces hors écran »

Une surface hors écran rend dans une texture de taille donnée : new WebGpuOffscreenSurface(width, height, format?). Sa méthode readPixels() renvoie les pixels sous forme d’octets RGBA, lignes depuis le haut, sur tous les backends : captures d’écran, miniatures, tests.

Écrire une région d’une texture

Section intitulée « Écrire une région d’une texture »

backend.textures.writeTexture(texture, data, { region }) réécrit un rectangle d’un niveau, le reste conservé : un glyphe ajouté à un atlas, une tuile d’une carte. Les données ne contiennent que les rangées de la région, depuis le haut, sans remplissage ; layer choisit une couche d’un tableau (ou une face d’un cube), toutes les couches sinon, leurs régions l’une après l’autre.

Une région écrit un seul niveau, le premier par défaut (level pour un autre), et n’en calcule aucun : les autres niveaux gardent leur contenu jusqu’à leur écriture, ou un nouveau calcul par encoder.generateMipmaps(texture). Une région qui sort du niveau, ou qui n’est pas sur les blocs 4×4 d’un format compressé (sauf à ses bords droit et bas), lève une erreur.

Relire des textures

Section intitulée « Relire des textures »

backend.textures.readTexture(texture, region?) relit une région d’une texture de couleur (toute la texture par défaut), sans attendre le GPU : sa promesse est résolue une ou deux frames plus tard, avec le contenu qu’ont laissé les frames soumises avant. Les pixels viennent rangée par rangée depuis le haut, sans remplissage, dans le layout du format (4 octets par pixel pour r32uint).

La texture doit avoir l’usage copy-src (absent de l’usage par défaut) et un seul échantillon ; les textures de profondeur ne se relisent pas. Une région qui sort de la texture lève une erreur. WebGPU copie dans un buffer mappé, WebGL2 lit dans un pixel buffer sondé par une fence, Vulkan copie dans un buffer de l’hôte. pickIds repose dessus : voir la sélection au pixel.

Capacités

Section intitulée « Capacités »

backend.capabilities indique ce que prend en charge un backend, et le compilateur vérifie les programmes en conséquence :

Capacité Signification WebGL2
compute Étapes de calcul true (émulées)
emulatedCompute Calcul émulé par des dessins dans des textures true
storageBuffers Storage buffers true (textures de données)
maxVaryings Valeurs interpolées entre les étapes selon le contexte
renderableFormats Formats de couleur utilisables comme attachments (rgba16float) avec EXT_color_buffer_float
objectTable Les données des objets lues dans une table, par instance true (textures de données)
maxAnisotropy L’anisotropie la plus haute des samplers avec EXT_texture_filter_anisotropic, sinon 1
maxColorAttachments Cibles de couleur d’une passe MAX_DRAW_BUFFERS (au moins 4)
maxColorAttachmentBytesPerSample Octets par pixel des cibles de couleur (WebGPU) —
independentBlend Cibles d’un pipeline avec des mélanges différents false
indirectDraw Des draws dont le GPU écrit les arguments —
multiDrawIndirect Plusieurs draws indirects en une commande —
drawIndirectCount Leur nombre écrit par le GPU —

Un graphe qui utilise une fonctionnalité absente échoue à la compilation avec une erreur explicite ; testez la capacité pour proposer une solution de repli.

Mipmaps et filtrage anisotrope

Section intitulée « Mipmaps et filtrage anisotrope »

Une texture créée avec mipLevelCount a des niveaux de détail, chacun de la moitié de la taille du précédent ; fullMipLevelCount(dimensions) donne la chaîne complète, jusqu’à 1×1. Les données écrites remplissent le premier niveau, et le backend calcule les autres à partir de lui, sur le GPU :

Après un rendu dans une telle texture, encoder.generateMipmaps(texture) recalcule ses niveaux (dans un render graph : addMipmapPass). Les textures sRGB sont moyennées en couleurs linéaires. Les niveaux sont réservés aux textures 2d, 2d-array et cube de formats de couleur, non multiéchantillonnées : les autres textures refusent mipLevelCount > 1.

std.textureSample choisit le niveau d’après la taille du pixel sur la texture ; std.textureSampleLevel lit un niveau donné. Ce dernier est disponible dans toutes les étapes : passez-lui un uv par std.perFragment, sinon il échantillonne aux sommets et interpole les couleurs.

Le filtrage anisotrope garde une texture nette sur une surface vue en incidence rasante (un sol, une route) : le sampler prend jusqu’à maxAnisotropy échantillons dans la direction où la texture est étirée.

  • Il demande les trois filtres linear (ceux par défaut) : une anisotropie demandée avec un filtre nearest lève une erreur, comme l’exige WebGPU. La valeur par défaut ne s’applique qu’aux samplers qui peuvent s’en servir, hors samplers de comparaison.
  • Les valeurs au-delà de capabilities.maxAnisotropy y sont ramenées (16 sur la plupart des GPU, 1 quand l’appareil n’a pas de filtrage anisotrope).
  • Il va avec les mipmaps : sans niveaux, une texture réduite scintille quelle que soit l’anisotropie.

Chaque backend calcule les niveaux à sa façon : generateMipmap en WebGL2, une passe de rendu par niveau en WebGPU, vkCmdBlitImage en Vulkan.

Ce que les backends absorbent

Section intitulée « Ce que les backends absorbent »

Le moteur suit les conventions de WebGPU ; les autres backends s’adaptent :

  • La profondeur dans l’espace clip va de 0 à 1. Les vertex shaders GLSL la ramènent à l’intervalle −1 à 1 d’OpenGL.
  • Origine du framebuffer : les images sont lues à partir de la ligne du haut partout. WebGL2 retourne ses viewports ; Vulkan utilise une hauteur de viewport négative, de sorte que y pointe vers le haut dans l’espace clip.
  • Bind groups : GLSL ES n’en a pas. Le pipeline WebGL2 attribue un point de binding à chaque uniform block et une unité de texture à chaque paire texture–sampler ; sous Vulkan, les groupes sont des descriptor sets.
  • Disposition des uniforms : règles WGSL sous WebGPU, std140 sous WebGL2 et Vulkan ; les programmes compilés ne connaissent que la disposition logique, le backend résout les offsets.
  • Enregistrement des commandes : WebGL2 enregistre les commandes d’une frame et les exécute lors de submit(), de sorte que les écritures dans les buffers sont vues par chaque draw, comme en WebGPU. Vulkan les écrit sous forme de mots de 32 bits, rejoués en un seul appel natif.
  • Synchronisation : WebGPU et WebGL2 sont synchronisés implicitement. La bibliothèque Vulkan suit la dernière utilisation de chaque texture et de chaque buffer, et insère les barrières.
  • Profondeur : depth24plus est une profondeur flottante sur 32 bits sous Vulkan, et depth24plus-stencil8 une profondeur flottante sur 32 bits avec un stencil sur 8 bits sous Vulkan et Direct3D 12. La référence du stencil est dynamique dans chaque pipeline Vulkan.

Données des objets et instanciation

Section intitulée « Données des objets et instanciation »

Les données de chaque objet dessiné — ses matrices monde et normale, 112 octets — forment une ligne d’une table d’objets, créée par backend.createObjectTable(). Un objet garde sa ligne tant qu’il existe ; la ligne n’est réécrite que lorsqu’il bouge, et les lignes écrites dans une frame partent vers le GPU en une seule plage. Chaque passe écrit les lignes des instances qu’elle dessine, dans son ordre, puis lie la table une seule fois.

Un draw indique firstInstance : son instance i lit la ligne instances[firstInstance + i]. Les objets qui se suivent avec le même pipeline, le même matériau et le même mesh forment un seul draw de plusieurs instances — le renderer trie par pipeline, matériau, puis mesh pour les regrouper. renderer.stats.get('scene') donne drawn (les objets) et drawCalls (les draws).

Backend Table d’objets Première instance
WebGPU Deux storage buffers : les lignes, la ligne de chaque instance instance_index l’inclut
Vulkan Deux storage buffers SV_InstanceID (l’InstanceIndex de Vulkan) l’inclut
WebGL2 Deux textures de données (RGBA32F, R32UI) lues avec texelFetch Un uniform défini avant chaque draw (pas de base instance)

Le Renderer a besoin de createObjectTable : un backend personnalisé l’implémente (un GpuObjectTable : writeRows, writeInstances), ainsi que le binding object-table des programmes.

Le culling sur le GPU

Section intitulée « Le culling sur le GPU »

Avec gpuCulling: true, les passes de scène laissent au GPU le test de chaque objet contre le frustum :

Le CPU regroupe toujours les objets en draws (par pipeline, matériau et mesh), mais n’écrit plus leurs instances : une passe de calcul teste la boîte de chacun, écrit les lignes de ceux qui sont dans le champ dans les instances de la table, dans leur ordre, et les arguments de chaque draw (le nombre d’instances, la première). Les passes dessinent ensuite par drawIndexedIndirect et drawIndirect, un par draw comme avant. L’image est la même.

  • Les listes d’objets ne sont plus testées sur le CPU ; une source (une scène) culle toujours ce qu’elle contient avec son octree. Les statistiques de la vue comptent les objets donnés au GPU.
  • Là où le backend a indirectDraw et des compute shaders : Vulkan, Direct3D 12, WebGPU avec indirect-first-instance. Ignoré en WebGL2.
  • Les draws lisent leurs arguments dans un buffer d’usage indirect : pass.drawIndirect(buffer, offset) (4 u32 : sommets, instances, premier sommet, première instance) et pass.drawIndexedIndirect(buffer, offset) (5 u32 : indices, instances, premier indice, sommet de base, première instance). Une passe de calcul peut écrire les instances de la table dans table.instanceBuffer.

Le culling sur le GPU entraîne le reste de ce que le GPU peut choisir lui-même :

  • L’occlusion culling sans retard : avec un OcclusionCulling, les objets visibles à la frame précédente sont dessinés d’abord, puis les autres testés contre la pyramide de profondeur de ce qu’ils ont dessiné, dans la même frame (voir le tutoriel de l’occlusion culling).
  • Les clusters de lumières sont remplis par des passes de calcul, jusqu’à 1024 lumières ponctuelles et spots dans le champ (MaxGpuClusterLights ; le CPU au-delà) : les mêmes listes que sur le CPU, dans le même ordre.
  • Les niveaux d’une surface tessellée : levels: 'gpu' de PatchSurface (voir le tutoriel de la tessellation).

Une scène gardée sur le GPU

Section intitulée « Une scène gardée sur le GPU »

Avec le culling sur le GPU, le CPU prépare encore chaque objet que la scène donne pour la caméra. Une GpuScene garde ses objets sur le GPU : leurs boîtes, leurs lignes dans la table des objets et leurs lots (un par mesh et matériau) restent dans des buffers du GPU d’une frame à l’autre, et le GPU les teste tous à chaque frame. Le CPU prépare un lot par mesh et matériau, et n’écrit que ce qui change.

Un scene graph le fait tout seul : new Scene({ gpuScene: true }) garde ses renderers statiques dans sa propre GpuScene (scene.gpuScene), les ajoute et les retire, touche ceux qui bougent. Dessinez la scène comme d’habitude, avec gpuCulling : le renderer les prend là, et les requêtes de la scène les laissent de côté.

Sur 99 225 immeubles, le CPU d’une frame passe de 125 ms (cullés sur le GPU, préparés un par un) à 1 ms, quel que soit leur nombre ; avec les ombres du soleil, de 102 ms (cullés sur le CPU) à 4 ms.

  • Les objets statiques ne sont réécrits qu’après touch ; les objets dynamic, à chaque frame. Ajouter ou retirer des objets les range tous à nouveau.
  • Les objets transparents sont dessinés comme d’habitude (triés à chaque frame).
  • Les shadow maps cullent aussi ses projeteurs sur le GPU, tuile par tuile, avec les mêmes lots et draws multiples que la caméra (voir plus bas).
  • Les layers des vues ne s’appliquent pas ; plusieurs renderers peuvent dessiner la même GpuScene. Elle se donne avec une source et des items.
  • Un scene graph y garde ses renderers statiques opaques vus de tous les layers : ni ceux qui sont cachés, ni ceux d’un lot statique, ni les niveaux de détail, qui changent souvent. Ses nœuds dynamiques restent dans ses requêtes.
  • Là où le backend ne culle pas sur le GPU (WebGL2), ses objets sont dessinés comme une liste (ceux d’un scene graph, depuis ses requêtes).

Les ombres cullées sur le GPU

Section intitulée « Les ombres cullées sur le GPU »

Les projeteurs d’une GpuScene sont cullés sur le GPU pour chaque tuile de l’atlas des ombres, après la caméra : la boîte de chacun contre le frustum de la tuile, puis, pour les lumières directionnelles, contre les récepteurs que la caméra dessine. Vu de la lumière, un masque de 32 × 32 cellules garde le récepteur le plus lointain de chacune ; un projeteur n’est dessiné que si l’une des cellules qu’il couvre a un récepteur derrière lui. Avec l’occlusion en deux phases, les ombres les suivent : les projeteurs de ce que la première dessine, puis, dans le même atlas, ceux de ce que la seconde trouve. Ce que le mouvement découvre a ses ombres dans la frame où il apparaît.

Rien à régler : gpuCulling et une GpuScene (ou une scène qui en garde une) suffisent. Sur la ville de 99 225 immeubles vue de son avenue, les passes des ombres passent de 0,73 ms (tous les projeteurs dans le frustum du soleil) à 0,07 ms, et leur culling coûte 0,23 ms.

Les récepteurs sont des boîtes : une grande (un seul sol sous toute la ville) couvre toutes les cellules, et garde tous les projeteurs devant elle. Découpez-la en dalles, comme la ville (tiledGround), pour que le test trouve ce qui est vu.

Des meshes qui partagent leurs buffers

Section intitulée « Des meshes qui partagent leurs buffers »

Les meshes d’une MeshArena de même format partagent un vertex buffer et un index buffer : le renderer place chacun à un sommet de base et un premier indice à lui (le premier emplacement libre ; les buffers doublent quand ils sont pleins, leur contenu recopié par le GPU) et les dessine de là, en indirect.

Cullés sur le GPU, les draws consécutifs de meshes d’une arène qui partagent un pipeline et un matériau deviennent un draw multiple (multiDrawIndexedIndirect, 1024 draws au plus). Avec drawIndirectCount, le GPU tasse les draws qui ont gardé des instances et écrit leur nombre : les draws vides ne sont même pas lancés. Sans arène, ou en WebGL2, rien ne change.

  • pass.multiDrawIndirect(buffer, offset, maxCount, count?) et pass.multiDrawIndexedIndirect(…) : maxCount draws, à 20 octets d’intervalle (les arguments de drawIndirect puis un u32 inutilisé ; ceux de drawIndexedIndirect), ou les count.buffer[count.offset] premiers. Vulkan (multiDrawIndirect, drawIndirectCount) et Direct3D 12 (ExecuteIndirect, 2048 draws au plus, le nombre dans un autre buffer que les arguments) nativement ; WebGPU par un draw chacun, sans nombre.
  • mesh.setGpuVertexCount({ buffer, offset }) : le nombre de sommets d’un mesh sans indices écrit par le GPU (une passe de calcul de la frame) ; le renderer le recopie dans les arguments de son draw.

Les données des meshes

Section intitulée « Les données des meshes »

Un Mesh garde ses données côté CPU ; le renderer les envoie au premier dessin du mesh, et de nouveau après setVertices ou setIndices.

  • Les mises à jour partielles : mesh.updateVertices(buffer, byteOffset, data) réécrit une partie d’un buffer de sommets (décalage et taille multiples de 4) : les renderers n’écrivent que ces octets dans le buffer qu’ils ont. Un renderer en retard de plus de 64 mises à jour renvoie tout le mesh.
  • Sur le GPU seulement : un mesh créé avec regenerate (une fonction qui refait ses données, telles qu’elles sont alors) rend sa copie CPU une fois qu’un renderer l’a envoyé (mesh.released) ; lire vertices ou indices la refait. mergeMeshes(parts, { source }) crée ainsi son mesh fusionné : les lots statiques ne gardent leur géométrie que sur le GPU.

Pipelines

Section intitulée « Pipelines »

Les pipelines sont créés à leur première utilisation, ce qui peut bloquer une frame pendant la compilation d’un shader. new Renderer(backend, { asyncPipelines: true }) les crée plutôt en arrière-plan : un élément est ignoré tant que son pipeline n’est pas prêt, et await renderer.whenReady() attend ceux en cours (un écran de chargement). WebGL2 lie les programmes en parallèle lorsque le navigateur dispose de KHR_parallel_shader_compile.

Le stencil

Section intitulée « Le stencil »

Le depthStencil d’un pipeline peut tester et écrire un stencil, sur un format de profondeur qui en a un (depth24plus-stencil8), sur les quatre backends :

  • stencilFront et stencilBack (les faces de primitive.frontFace) : compare (always par défaut) compare la référence au stencil, puis failOp, depthFailOp et passOp (keep par défaut) le modifient quand le test de stencil échoue, quand le test de profondeur échoue, quand les deux réussissent : keep, zero, replace (par la référence), invert, increment-clamp, decrement-clamp, increment-wrap, decrement-wrap. Avec l’une des faces, le test de stencil est actif ; sans, il ne l’est pas.
  • stencilReadMask et stencilWriteMask : les bits comparés et écrits (0xff par défaut).
  • pass.setStencilReference(reference) : la référence des draws suivants, de 0 à 255 ; 0 au début de chaque passe.
  • L’attachment de profondeur d’une passe : stencilLoad (clear ou load, celui de la profondeur par défaut) et stencilClearValue (0 par défaut).

Un test de stencil, des masques ou des options de stencil sur un format sans stencil lèvent une erreur plutôt que d’être ignorés.
