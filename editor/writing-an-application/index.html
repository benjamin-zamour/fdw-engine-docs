Building a web application on the editor

An application built on the editor supplies a profile, plugins, the parts of its plugins that run with the engine, and the scenes it needs. The SDK provides the browser engine host, the viewport, browser file dialogs, and IndexedDB storage; the shell remains EditorShell. For an Electron application, see the separate desktop application tutorial.

The SDK has separate web and desktop entry points. This tutorial is the project the CI builds out of the repository, from the npm archives of the packages: what follows installs, typechecks, builds, and runs as written.

2. Define the application profile

Section titled “2. Define the application profile”

The profile belongs to the application, not to the editor’s built-in profile table. Include the built-in plugins that the shell needs, the plugin of this application and the plugin package of step 5:

The profile restricts the shell’s UI; it is not a security boundary. Plugins in an application are trusted code. See Profiles and views for command allow/deny rules and layout behavior.

3. Add an engine extension

Section titled “3. Add an engine extension”

The part of a plugin that runs with the engine is an engine extension: it sees the scene shown, works before each frame, and exchanges messages with its plugin under the plugin’s ID. This one counts the frames and answers when its plugin asks:

On the web, the engine runs in the page; in a desktop application, in its engine process. The messages are the same: structured-cloneable values, and bytes as a Uint8Array when needed.

4. Add a local plugin

Section titled “4. Add a local plugin”

A plugin declares its contributions before its code is loaded. Its command and view IDs use the same prefix as the plugin. Its panel reaches the extension through extensionChannel, on the connection of the editor:

The application passes this plugin to its host, and the extension to its engine. The profile selects the plugin; it does not install or discover plugins.

6. Leave a plugin out of a profile

Section titled “6. Leave a plugin out of a profile”

The host can be given more plugins than the profile selects: one build serving several profiles, for example, a reviewer’s and an administrator’s. A plugin the profile does not list is not registered: its commands and panels appear nowhere, and its load never runs. With a dynamic import(), its code stays in a chunk of its own, which the page never downloads.

The profile is a selection of the UI, not a security boundary: the code of a plugin left out is still part of the deployed site.

7. Compose and start the web application

Section titled “7. Compose and start the web application”

startWebApplication starts the application in one call: the engine on a canvas with the scenes and the extensions of its plugins, the host with its profile and plugins (IndexedDB, the file dialogs of the browser), the shell rendered into #root, and the engine stopped when the page goes.

Replace createShadowsScene with the scene factories of your application. The WebGPU backend is preferred and WebGL2 is available as a fallback; the backend option can select one explicitly. The About panel shows the scene and the frames the extension counted.

The address of the page takes the launch options of the SDK (readLaunchOptions): ?backend=webgl2, ?scene=, ?open=<url> (a model opened at the start; the open option gives one by default), ?view= (a panel opened), ?docks=bottom,right, ?embed (nothing kept), ?api (driven by the page around the frame, through @fdw/viewer-embed). onRuntime receives the runtime once made, for what is the application’s own.

The shell keeps the layout of each profile in the storage of the host (IndexedDB on the web, a file of the user’s data on the desktop): the panels opened and closed, the docks and the toolbars are found again at the next start. View → Reset layout restores the layout of the profile. ?embed keeps nothing.

For a host of your own (another storage, another root, React around the shell), compose WebEngine, createWebHost and EditorShell yourself: startWebApplication is made of them.

The products of the repository are built this way, and run with one command each: npx nx dev viewer, npx nx dev review, npx nx dev material-editor, npx nx dev game-editor, npx nx dev simulation (Architecture guidelines).

8. Build and deploy

Section titled “8. Build and deploy”

Run the regular Vite commands:

The built site is static and can be deployed under a subpath with Vite’s base option (npx vite build --base /acme/). Add this blank page to public/, which Vite copies to the root of the site: the host opens it to show detached panels in a separate window.

The packages are not published on npm yet. To try them, pack them from the repository with node tools/sdk/pack.mjs, then install the archives of tmp/sdk-package/archives in place of the package names; node tools/sdk/verify-external.mjs does it all on this tutorial. For a desktop application, continue with the desktop application tutorial, which reuses the profile, the plugin and the extension of this one.
