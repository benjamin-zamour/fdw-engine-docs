Backends and surfaces

Three objects separate an application from the graphics API it runs on.

Object Role Interface (@fdw/engine-backend)
Engine The device: created by init(), released by destroy(); its state is a signal Engine
Surface Where frames go: a canvas, a window, a texture. width, height, format, present() Surface
RenderBackend What renderers use: buffer, texture and pipeline factories, math, command encoding RenderBackend, engine.backend

The Renderer, the materials and the render graph only see the RenderBackend and the Surface: code written against them runs everywhere.

The backends

Section titled “The backends”
Backend Package Engine Surfaces Shaders
WebGPU @fdw/engine-webgpu WebGpuEngine WebGpuSurface (canvas), WebGpuOffscreenSurface WGSL
WebGL2 @fdw/engine-webgl2 WebGl2Engine WebGl2CanvasSurface, WebGl2OffscreenSurface GLSL ES 3.00
Dawn @fdw/engine-native createDawnEngine() DawnWindowSurface, WebGpuOffscreenSurface WGSL
Vulkan @fdw/engine-vulkan VulkanEngine VulkanWindowSurface (@fdw/engine-native), VulkanOffscreenSurface HLSL, compiled to SPIR-V by DXC

Every backend passes the same rendering test suite.

Offscreen surfaces

Section titled “Offscreen surfaces”

An offscreen surface renders into a texture of a given size: new WebGpuOffscreenSurface(width, height, format?). Its readPixels() returns the pixels as RGBA bytes, rows from the top, on every backend: screenshots, thumbnails, tests.

Writing a region of a texture

Section titled “Writing a region of a texture”

backend.textures.writeTexture(texture, data, { region }) rewrites a rectangle of a level, the rest kept: a glyph added to an atlas, a tile of a map. The data holds the rows of the region only, from the top, tightly packed; layer picks a layer of an array (or a face of a cube), every layer otherwise, their regions one after the other.

A region writes one level, the first by default (level for another), and computes none: the other levels keep their content until written, or computed again by encoder.generateMipmaps(texture). A region out of the level, or not on the 4×4 blocks of a compressed format (except at its right and bottom edges), throws.

Reading textures back

Section titled “Reading textures back”

backend.textures.readTexture(texture, region?) reads a region of a color texture back (the whole texture by default), without waiting for the GPU: its promise resolves a frame or two later, with the content the frames submitted before left. The pixels come rows from the top, tightly packed, in the layout of the format (4 bytes per pixel for r32uint).

The texture needs the copy-src usage (not in the default usage) and a single sample; depth textures cannot be read. A region out of the texture throws. WebGPU copies into a mapped buffer, WebGL2 reads into a pixel buffer polled by a fence, Vulkan copies into a host buffer. pickIds is built on it: see Picking.

Mipmaps and anisotropic filtering

Section titled “Mipmaps and anisotropic filtering”

A texture created with mipLevelCount has levels of detail, each half the size of the previous one; fullMipLevelCount(dimensions) gives the whole chain, down to 1×1. The data written fill the first level, and the backend computes the others from it, on the GPU:

After rendering into such a texture, encoder.generateMipmaps(texture) computes its levels again (in a render graph: addMipmapPass). The sRGB textures are averaged in linear colors. Levels are for the 2d, 2d-array and cube textures of color formats, not multisampled: the other textures refuse mipLevelCount > 1.

std.textureSample chooses the level from the size of the pixel on the texture; std.textureSampleLevel reads a given one. The latter is available in every stage: give it a uv through std.perFragment, or it samples at the vertices and interpolates the colors.

Anisotropic filtering keeps a texture sharp on a surface seen at a grazing angle (a floor, a road): the sampler takes up to maxAnisotropy samples along the direction in which the texture is stretched.

  • It needs the three filters linear (the default): an anisotropy asked with a nearest filter throws, as WebGPU requires. The default only applies to the samplers that can use it, comparison samplers excepted.
  • Values above capabilities.maxAnisotropy are clamped to it (16 on most GPUs, 1 where the device has no anisotropic filtering).
  • It works with the mipmaps: without levels, a minified texture flickers whatever the anisotropy.

The backends compute the levels each in their way: generateMipmap in WebGL2, a render pass per level in WebGPU, vkCmdBlitImage in Vulkan.

What the backends absorb

Section titled “What the backends absorb”

The engine follows the conventions of WebGPU; the other backends adapt:

  • Clip space depth goes from 0 to 1. The GLSL vertex shaders remap it to the −1 to 1 of OpenGL.
  • Framebuffer origin: images are read from the top row everywhere. WebGL2 flips its viewports; Vulkan uses a negative viewport height, so that y points up in clip space.
  • Bind groups: GLSL ES has none. The WebGL2 pipeline assigns a binding point to each uniform block and a texture unit to each texture–sampler pair; on Vulkan, groups are descriptor sets.
  • Uniform layouts: WGSL rules on WebGPU, std140 on WebGL2 and Vulkan; the compiled programs know only the logical layout, the backend resolves the offsets.
  • Command recording: WebGL2 records the commands of a frame and runs them on submit(), so that buffer writes are seen by every draw, as in WebGPU. Vulkan writes them as 32-bit words, replayed in one native call.
  • Synchronization: WebGPU and WebGL2 are implicitly synchronized. The Vulkan library tracks the last use of each texture and buffer, and inserts the barriers.
  • Depth: depth24plus is a 32-bit float depth on Vulkan, and depth24plus-stencil8 a 32-bit float depth with an 8-bit stencil on Vulkan and Direct3D 12. The stencil reference is dynamic in every Vulkan pipeline.

Object data and instancing

Section titled “Object data and instancing”

The data of each object drawn — its world and normal matrices, 112 bytes — is a row of an object table, created by backend.createObjectTable(). An object keeps its row while it lives; the row is written again only when it moves, and the rows written in a frame go to the GPU in one range. Each pass writes the rows of the instances it draws, in its order, then binds the table once.

A draw gives firstInstance: its instance i reads the row instances[firstInstance + i]. The objects that follow each other with the same pipeline, material and mesh are one draw of several instances — the renderer sorts by pipeline, material, then mesh to gather them. renderer.stats.get('scene') gives drawn (the objects) and drawCalls (the draws).

Backend Object table First instance
WebGPU Two storage buffers: the rows, the row of each instance instance_index includes it
Vulkan Two storage buffers SV_InstanceID (the InstanceIndex of Vulkan) includes it
WebGL2 Two data textures (RGBA32F, R32UI) read with texelFetch A uniform set before each draw (no base instance)

The Renderer needs createObjectTable: a backend of your own implements it (a GpuObjectTable: writeRows, writeInstances), and the object-table binding of the programs.

Culling on the GPU

Section titled “Culling on the GPU”

With gpuCulling: true, the scene passes leave the test of each item against the frustum to the GPU:

The CPU still gathers the items into draws (by pipeline, material and mesh), but no longer writes their instances: a compute pass tests the box of each one, writes the rows of those in view into the instances of the table, in their order, and the arguments of each draw (how many instances, the first one). The passes then draw with drawIndexedIndirect and drawIndirect, one per draw as before. The image is the same.

  • The lists of items are no longer tested on the CPU; a source (a scene) still culls what it holds with its octree. The statistics of the view count the items given to the GPU.
  • Where the backend has indirectDraw and compute shaders: Vulkan, Direct3D 12, WebGPU with indirect-first-instance. Ignored on WebGL2.
  • The draws read their arguments from a buffer with the indirect usage: pass.drawIndirect(buffer, offset) (4 u32: vertices, instances, first vertex, first instance) and pass.drawIndexedIndirect(buffer, offset) (5 u32: indices, instances, first index, base vertex, first instance). A compute pass can write the instances of the table in table.instanceBuffer.

The culling on the GPU brings along the rest of what the GPU can choose itself:

  • The occlusion culling without delay: with an OcclusionCulling, the objects visible at the previous frame are drawn first, then the others are tested against the depth pyramid of what they drew, in the same frame (see the occlusion culling tutorial).
  • The light clusters are filled by compute passes, up to 1024 point and spot lights in view (MaxGpuClusterLights; the CPU beyond): the same lists as on the CPU, in the same order.
  • The levels of a tessellated surface: levels: 'gpu' of PatchSurface (see the tessellation tutorial).

A scene kept on the GPU

Section titled “A scene kept on the GPU”

With the culling on the GPU, the CPU still prepares each object the scene gives for the camera. A GpuScene keeps its objects on the GPU instead: their boxes, their rows in the object table and their runs (one per mesh and material) stay in GPU buffers from frame to frame, and the GPU tests them all at each frame. The CPU prepares one run per mesh and material, and writes only what changed.

A scene graph does it by itself: new Scene({ gpuScene: true }) keeps its static renderers in its own GpuScene (scene.gpuScene), adds and removes them, touches those that move. Draw the scene as usual, with gpuCulling: the renderer takes them from there, and the queries of the scene leave them out.

On 99 225 buildings, the CPU of a frame goes from 125 ms (culled on the GPU, prepared one by one) to 1 ms, whatever their number; with the shadows of the sun, from 102 ms (culled on the CPU) to 4 ms.

  • Static objects are written again only after touch; dynamic ones at each frame. Adding or removing objects lays them all out again.
  • The transparent objects are drawn as usual (sorted each frame).
  • The shadow maps cull its casters on the GPU too, tile by tile, in the same runs and multiple draws as the camera (see below).
  • The layers of the views do not apply; several renderers can draw the same GpuScene. It can be given besides a source and items.
  • A scene graph keeps there its opaque static renderers seen by every layer: not the hidden ones, those of a static batch, nor the levels of detail, which switch often. Its dynamic nodes stay in its queries.
  • Where the backend cannot cull on the GPU (WebGL2), its objects are drawn as a list (those of a scene graph, from its queries).

Shadows culled on the GPU

Section titled “Shadows culled on the GPU”

The casters of a GpuScene are culled on the GPU for each tile of the shadow atlas, after the camera: the box of each against the frustum of the tile, then, for the directional lights, against the receivers the camera draws. Seen from the light, a mask of 32 × 32 cells keeps the farthest receiver of each; a caster is drawn only if one of the cells it covers has a receiver behind it. With the occlusion culling in two phases, the shadows follow them: the casters of what the first phase draws, then, over the same atlas, those of what the second finds. What moving reveals has its shadows in the frame it appears.

Nothing to set: gpuCulling and a GpuScene (or a scene keeping one) are enough. On the city of 99 225 buildings seen from its avenue, the shadow passes go from 0.73 ms (every caster in the frustum of the sun) to 0.07 ms, and their culling costs 0.23 ms.

The receivers are boxes: a large one (a single ground under the whole city) covers every cell, and keeps every caster in front of it. Cut it in tiles, as the city does (tiledGround), for the test to find what is seen.

Meshes sharing their buffers

Section titled “Meshes sharing their buffers”

The meshes of a MeshArena with the same layout share one vertex buffer and one index buffer: the renderer places each at a base vertex and a first index of its own (first fit; the buffers double when full, their content copied by the GPU) and draws them indirectly from there.

Culled on the GPU, the consecutive draws of meshes of an arena sharing a pipeline and a material become one multiple draw (multiDrawIndexedIndirect, at most 1024 draws). With drawIndirectCount, the GPU packs the draws that kept instances and writes their number: the empty ones are not even issued. Without an arena, or on WebGL2, nothing changes.

  • pass.multiDrawIndirect(buffer, offset, maxCount, count?) and pass.multiDrawIndexedIndirect(…): maxCount draws, 20 bytes apart (the arguments of drawIndirect then an unused u32; those of drawIndexedIndirect), or the first count.buffer[count.offset] of them. Vulkan (multiDrawIndirect, drawIndirectCount) and Direct3D 12 (ExecuteIndirect, at most 2048 draws, the count in another buffer than the arguments) natively; WebGPU by a draw each, without count.
  • mesh.setGpuVertexCount({ buffer, offset }): the vertex count of a mesh without indices written by the GPU (a compute pass of the frame); the renderer copies it into the arguments of its draw.

Mesh data

Section titled “Mesh data”

A Mesh holds its data on the CPU; the renderer uploads it when the mesh is first drawn, and again after setVertices or setIndices.

  • Partial updates: mesh.updateVertices(buffer, byteOffset, data) rewrites a part of a vertex buffer (offset and size in multiples of 4): the renderers write only these bytes to the buffer they have. A renderer more than 64 updates behind uploads the whole mesh again.
  • GPU only: a mesh made with regenerate (a function that makes its data again, as it is then) gives its CPU copy back once a renderer uploaded it (mesh.released); reading vertices or indices makes it again. mergeMeshes(parts, { source }) makes its merged mesh so: the static batches keep their geometry on the GPU only.

Pipelines

Section titled “Pipelines”

Pipelines are created on first use, which can stall a frame while a shader compiles. new Renderer(backend, { asyncPipelines: true }) creates them in the background instead: an item is skipped until its pipeline is ready, and await renderer.whenReady() waits for the pending ones (a loading screen). WebGL2 links the programs in parallel when the browser has KHR_parallel_shader_compile.

The stencil

Section titled “The stencil”

The depthStencil of a pipeline can test and write a stencil, on a depth format that has one (depth24plus-stencil8), on the four backends:

  • stencilFront and stencilBack (the faces of primitive.frontFace): compare (always by default) compares the reference with the stencil, then failOp, depthFailOp and passOp (keep by default) change it when the stencil test fails, when the depth test fails, when both pass: keep, zero, replace (by the reference), invert, increment-clamp, decrement-clamp, increment-wrap, decrement-wrap. With either face given, the stencil test is on; without, it is off.
  • stencilReadMask and stencilWriteMask: the bits compared and written (0xff by default).
  • pass.setStencilReference(reference): the reference of the next draws, from 0 to 255; 0 at the beginning of each pass.
  • The depth attachment of a pass: stencilLoad (clear or load, that of the depth by default) and stencilClearValue (0 by default).

A stencil test, masks, or stencil options on a format without stencil throw an error rather than being ignored.
