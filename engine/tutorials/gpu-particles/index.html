GPU particles

A fountain of 4096 particles: each frame, a compute graph moves every particle from its previous state to the next one, and a material draws a small quad at each position. The simulation never leaves the GPU, on every backend, WebGL2 included.

…

The Compute tutorial introduces compute graphs and storage buffers; this one builds a simulation on them.

The state of a particle

Section titled “The state of a particle”

Each particle has a position, an age and a velocity: two vec4 per particle, in two storage buffers. The age is in the w of the position.

A compute graph cannot read a buffer it writes: its threads run in any order, and one thread could read a particle another one already moved. The state is therefore kept twice: the step reads one copy and writes the other, and the two swap at each frame.

A third buffer holds the launch velocity of each particle, read when it starts again.

The simulation step

Section titled “The simulation step”

One thread per particle. It reads the particle, adds the gravity to its velocity and its velocity to its position. At the end of its life, the particle starts again from the origin: the graph has no branch, so std.select chooses between the two results.

On WebGL2

Section titled “On WebGL2”

WebGL2 has no compute shaders: the same graph runs there by rendering to textures, the GPGPU technique that predates compute shaders.

  • Each storage buffer has a copy in a data texture, 16 bytes per texel.
  • Each write of the graph becomes a draw of points: one point per thread, placed by the vertex shader on the texel of the element written, and whose value the fragment shader writes. The step above makes two draws, one per buffer written.
  • The engine copies each buffer to its texture and back on the GPU, when a use needs it: a dispatch, a draw, read().

The code does not change. The example shows, under the canvas, which way the backend computes. The Compute guide details what WebGL2 does not do: indirect dispatches, mainly.
