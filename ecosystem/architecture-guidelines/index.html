Architecture guidelines

The repository is a set of platforms (the engine, the editor), of independent foundations (shared, conversion, geometry), of products that put them together (apps/) and of labs that try them out. This page gives the rules for placing code. Read it before adding a package or moving one; Repository structure shows the result.

The domains

Section titled “The domains”
Domain Owns Does not own
shared/ What every domain needs and no domain owns: the capabilities, the view state Code used by two products: it has an owner
conversion/ The pivot model: 3D scenes and CAD models in memory, the conversion reports The formats that need the kernel: geometry/
geometry/ The geometric kernel, its implementations (OpenCascade), the readers of exact formats Meshes for the GPU: engine/
engine/ The runtime: rendering, backends, scene, resources, modules, adapters, its extensions Any user interface, any DOM in its core
editor/ The platform the products are built on: interface, SDK and its hosts, graph editor, project, shared plugins The features of one product: apps/<product>/
labs/ The demos (of the engine, of the editor on its SDK), their scenes, the experiments and prototypes Anything a product needs to run
apps/ The products sold to the customers, one directory each, with their private plugins; the documentation Code another product needs: it moves down

Two questions decide the domain of a package:

  1. What does it know? A package that draws knows the engine; a package with React panels knows the editor. It goes to the lowest domain that holds everything it imports.
  2. Who would use it alone? The pivot is used by converters without the engine: it stays out of engine/. A STEP reader needs the kernel: it is in geometry/, not in conversion/.

shared/ is the exception, not the default: a package goes there only when it depends on nothing and no domain is a better owner. Being used by two domains is not a reason.

The dependencies

Section titled “The dependencies”

The domains are layers. A library depends only on its domain and those below it:

A library of May import
shared shared
conversion shared, conversion
geometry shared, conversion, geometry
engine shared, conversion, geometry, engine
editor shared, conversion, geometry, engine, editor
labs, apps Anything but an application

And whatever the domain:

  • No library imports the labs nor an application. The editor does not take a demo scene to fill its sample level: the primitives it needs are in engine-core, the contract of a running scene in engine-runtime.
  • The engine does not know the editor. The editing on the side of the engine (engine-editing, engine-graph-editing) has no DOM; the editor builds on it.
  • The engine reads the pivot through adapters. engine-pivot and engine-gltf turn pivot models into engine resources and back; the pivot carries the material graphs as data (MaterialGraphDocument), which the adapter checks with parseGraph.
  • A test follows the same rules. A test that needs a higher domain lives in a package of that domain: the end of the STEP tutorial, written in glTF, is tested by engine-pivot, not by pivot-step.
  • No cycle: the graph is in layers.

The lint checks them: @nx/enforce-module-boundaries in eslint.config.mjs reads the tag scope: of each project and refuses an import that goes up. npx nx run-many -t lint runs it, and so does the CI. When the lint refuses an import, move the code to the right domain or invert the dependency (an interface below, its implementation above): never widen the rule for one package.

The plugins

Section titled “The plugins”

There is no plugin system for the whole repository: each platform has its own contract, and its plugins live with it.

Where Owner For
engine/plugins/ Engine Extensions of the runtime loaded through a plugin mechanism
editor/plugins/ Editor Plugins shared by the applications built on the editor
apps/<product>/plugins/ The product Plugins private to one product
  • An implementation is not a plugin. engine-physics-rapier implements the API of engine-physics: it is a package of engine/, not of engine/plugins/.
  • A plugin starts where it is used. A plugin written for one product goes in apps/<product>/plugins/. Do not guess a future reuse.
  • A plugin used by a second product is promoted to the plugins of its platform, after checking that it depends on nothing of its product: node tools/repo/move.mjs apps/<product>/plugins/<name> editor/plugins/<name>.
  • A shared plugin never imports a product. The product configures it.

The editor is a platform

Section titled “The editor is a platform”

The editor is not a product: it is the platform the products are built on, through its SDK (@fdw/editor-application-sdk). The SDK holds the hosts: /web (the canvas engine, the browser host, the storage, the file dialogs) and /desktop (the Electron host, the connection to the engine process, the session of the engine); editor-native-viewport gives the native viewport. A product supplies its profile, its plugins and its scenes, and picks the hosts it ships with.

  • The editors of the repository are demos. labs/editor-web and labs/editor-desktop show the platform on the SDK: every profile, the plugins, the demo scenes. They are not shipped, and nothing imports them.
  • A product is built like them, in apps/<product>/, on the SDK and the shared plugins, never on the code of a demo.
  • What depends on the platform stays in the hosts. A product asks the host for files, storage, windows; it imports neither Electron nor the browser APIs itself. What a host lacks is added to the SDK.

The labs

Section titled “The labs”

labs/ holds what explores or shows the capabilities: the demos, the scenes they share, the experiments, the prototypes.

  • The labs run in the CI: being experimental does not exempt them from compiling and from their tests.
  • No product depends on the labs. A piece of a demo that a product needs moves to its domain first (as the primitives moved to engine-core).
  • The benchmarks of the measurement infrastructure stay in tools/bench/.

The products

Section titled “The products”

Each product is a directory of apps/, started by the SDK in the browser (startWebApplication) and on the desktop (startDesktopApplication, with @fdw/editor-electron): its profile, its plugins, its sample models, the same on both (src/product.ts). A product holds no feature: what it shows lives in the shared packages (the profile in editor-ui, the plugins in editor/plugins/, the engine in engine/), so that the demos, the documentation and the other products show the same code.

Product Phase Web (port) Desktop
viewer P27 npx nx dev viewer (4310) npx nx run viewer:desktop
review P28 npx nx dev review (4311) npx nx run review:desktop
material-editor P29 npx nx dev material-editor (4312) npx nx run material-editor:desktop
game-editor P20 npx nx dev game-editor (4313) npx nx run game-editor:desktop
simulation P31 npx nx dev simulation (4314) npx nx run simulation:desktop

npx nx build <product> builds it into apps/<product>/dist, and npx nx preview <product> serves the build. The viewer and the review open a sample model at the start (roller.step), the simulation a sample result (cantilever.vtu.series); ?open=<url> opens another, and the other launch options of the SDK apply (?backend=webgl2, ?view=, ?docks=, ?embed).

On the desktop, the engine runs natively (Vulkan, Direct3D 12 when asked for, Dawn as a fallback) in a viewport placed over the page; the first run installs the shared Electron toolchain (tools/electron) and builds the native addons. desktop-build builds it into apps/<product>/desktop/out, desktop-preview runs that build (the sample model opens only from the dev server: a page of file: cannot fetch it), typecheck-desktop checks its processes. A local Nx plugin gives these targets to every product with a desktop/electron.vite.config.ts (tools/apps/nx-desktop.mjs).

  • A new product copies one of them: a package.json (private, @fdw-engine/<product>), a project.json (scope:apps, type:app), index.html and popout.html, its src/ and its vite.config.mts; then npm install and npx nx sync. Its Nx name must not be one of a package (review, not design-review).
  • A feature it needs goes into its domain first (a panel into a plugin of editor/plugins/, a command into editor-ui); the product only composes it. Its private plugins, in apps/<product>/plugins/, are the exception: what no other product will show.
  • A product never imports another product, nor the labs: what two products share moves down to editor/ or to the domain that owns it.
  • On the desktop, its entry points are a line each: what differs from a product to another is in src/product.ts, the rest in @fdw/editor-electron. Launched from a terminal of VS Code’s extensions, unset ELECTRON_RUN_AS_NODE: Electron would start as Node.

Adding a package

Section titled “Adding a package”
  1. Pick its domain with the two questions above, and its directory: <domain>/<name>. Its name says its domain: engine-… in the engine, editor-plugin-… for a plugin of the editor.
  2. Copy a package of the same domain, such as engine/engine-input: package.json (name @fdw/<name>, exports pointing to ./src/index.ts), project.json, the tsconfig files, vitest.config.mts, README.md.
  3. Tag it in project.json: scope:<domain>, runtime:, type:lib (or type:plugin).
  4. Declare it: its path in tsconfig.base.json, its description and its field fdw in package.json (Package architecture).
  5. Install and check:

A new directory that holds projects (engine/plugins/, a product of apps/) is added to the workspaces of the root package.json and to projectParents in tools/repo/layout.mjs.

Moving a package

Section titled “Moving a package”

tools/repo/move.mjs moves directories and rewrites the paths that point into them: the relative paths of the configurations and the pages, and the paths from the root (engine/engine-core) in the workflows, the scripts and the documentation. The npm names and the Nx project names do not change, so no import does.

Then change its tag scope: if it changes domain, and read the diff: the tool rewrites a relative path only when it points to something that exists.
