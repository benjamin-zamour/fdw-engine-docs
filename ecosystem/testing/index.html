Testing

The tests use Vitest. npx nx run-many -t test runs all of them; npx nx test <project> one project; npx nx run-many -t test-unit the unit tests alone (see Continuous integration for the other families).

Unit tests

Section titled “Unit tests”

Next to the code, as src/**/*.spec.ts. They need no GPU:

  • engine-shader: graphs built, validated and compiled, checked on the IR (instructions, stages, layout) or on the diagnostics.
  • engine-core: the renderer and the render graph on a fake backend (src/testing/fakeBackend.ts), which records the resources created and the commands encoded: what is drawn, in which order, with which buffers.
  • Code generators: the generated code, on small programs.

The rendering suite

Section titled “The rendering suite”

tests/rendering renders the same scenes on every backend, through the whole engine, into offscreen surfaces, and compares pixels. A feature that changes what is drawn adds a test to src/suite.ts: it then runs on all backends at once.

File Backend Needs
dawn.spec.ts WebGPU on Dawn, in Node; then every program of the suite in HLSL and GLSL ES the webgpu package (installed); the Vulkan SDK (DXC, spirv-val, spirv-cross, glslangValidator) for the programs
webgl2.browser.spec.ts WebGL2, in headless Chromium npx playwright install chromium-headless-shell
vulkan.spec.ts Vulkan, with the validation layer the Vulkan SDK, and the addon built

Without the SDK, the Vulkan, HLSL and GLSL tests are skipped, not failed — unless they are required (see Continuous integration). On Vulkan, a test fails if the validation layer reports anything. dawn.spec.ts records the programs compiled by the suite on Dawn, then (programs.ts, as many programs at a time as there are cores):

  • compiles each of them in HLSL with DXC, validates the SPIR-V with spirv-val, and compares the uniform offsets of the layout with the reflection of spirv-cross;
  • generates them in GLSL ES 3.00 (the compute stages as the draws that emulate them on WebGL2), and validates and links them with glslangValidator, stricter than the compilers of the browsers.

Pixel tests check exact values where the GPU computes them exactly (clears, unlit colors), and ranges elsewhere (edges, filtering): the GPUs round differently.

The native packages

Section titled “The native packages”

engine-native and engine-vulkan test their TypeScript side with mock addons, and their native side on the real GPU when the addons are built. Their targets (test-native, test-vulkan, test-d3d12) depend on build-native, and their inputs include VULKAN_SDK, VK_DRIVER_FILES, FDW_REQUIRE_SUITES and the OS: Nx reruns them when these change.

Benchmarks

Section titled “Benchmarks”

*.bench.ts files measure the CPU cost of the renderer, the render graph, the scene, the ECS, the geometry and the shader compiler, on the fake backend: npx vitest bench in a package. Run them before and after a change on a hot path:

On every pull request, the Benchmarks workflow does the same on the CI: the change and its base measured in the same job, compared in the summary of the run. A benchmark is marked slower or faster beyond 20 % and beyond the margins of error of both measures. The runners are shared and noisy: the workflow never fails, the table is a hint to look closer.

Continuous integration

Section titled “Continuous integration”

Every pull request runs on GitHub Actions (.github/workflows/), and must be green to be merged into main. The checks are split into families of validation, each a Nx target you can run on your machine, and a job with its environment, its timeout and its reports:

Family Nx target Runs on What it tests
Static — Linux The format, typecheck and lint; the tests of tools/ci
Unit test-unit Linux The tests in Node, without GPU, browser, SDK or addon
Browser test-browser Linux, Windows The tests in Chromium (engine-audio-web, editor-web)
WebGL2 test-webgl2 Linux, Windows The rendering suite on WebGL2, in Chromium on SwiftShader
WebGPU test-webgpu Linux, Windows Dawn in Node; the programs of the suite in HLSL and GLSL ES
Vulkan test-vulkan Linux, Windows engine-vulkan, the rendering suite on lavapipe
Direct3D 12 test-d3d12 Windows engine-d3d12, the rendering suite on WARP
Native test-native Linux, Windows The addon of engine-native, its windows, the *-native packages
Editor test-editor Linux The desktop editor, end to end, in Electron
SDK package test-package Linux The web SDK tutorial, built outside the repository from npm archives
SDK desktop package test-desktop-package Linux The desktop SDK tutorial, built, packaged and started outside the repository, on lavapipe

tools/ci/select.mjs picks them: on a pull request, the projects the change affects (nx show projects --affected) that have the target of a family; everything when a global file changed (package-lock.json, nx.json, tsconfig*.json, tools/native/, tools/ci/, tools/sdk/, the workflow); everything on each push to main. A change of engine-webgl2 runs WebGL2, not Vulkan; a plugin of the editor runs no rendering suite. The rule of main requires one status, CI Required, which checks that each family selected succeeded and that the others were skipped. Build the documentation stays apart (see below).

The runners have no GPU: Vulkan runs on lavapipe (the software Vulkan of Mesa), Direct3D 12 on WARP, WebGL2 in Chromium on SwiftShader, the windows in a virtual display (Xvfb). Each family job publishes an artifact <family>-<os>: the JUnit report of the tests, the versions of the environment, the logs of the native builds; a failed job says in its summary whether it failed in the installation, the compilation or the tests.

On a workstation, a suite whose GPU, SDK, addon or display is missing is skipped. In the CI, FDW_REQUIRE_SUITES lists the suites that must run (vulkan, dawn,hlsl,glsl, native,window…): a missing one fails instead of passing silently. A new suite of this kind calls canRun(name, ready, reason) of @fdw/engine-backend/testing.

Where a test goes

Section titled “Where a test goes”
  • A unit test (*.spec.ts) opens no browser, no GPU adapter and no addon. It runs in test-unit.
  • A test that needs Dawn or a GPU in a package that also has unit tests is named *.gpu.spec.ts (engine-webgpu); a test in Chromium, *.browser.spec.ts; one that needs an addon, *.native.spec.ts.
  • A new package has the tags scope: (engine, editor, viewer, shared, docs, demo, testing, tooling), runtime: (universal, web, native), type: (lib, plugin, app, test), and backend: if it implements one; its dependencies in its package.json: they make the graph the selection reads.

The rules

Section titled “The rules”
  • No retry, no silent skip: a suite that cannot run fails. A job run again by hand is noted in the pull request (the job, the supposed cause).
  • No longer timeout to make a slow test pass: measure it (the JUnit report, the duration budget), fix the cause, or move the test to its family.
  • The duration budget compares each test to the median of its last five durations on main, for its family and OS: the slower ones are listed in the summary of the job, as warnings. It does not fail the pull request: the runners are shared and noisy.
  • An external resource (a binary, a SDK, a model) comes from a cache or a release of the repository, never from a free download during a test.
  • A new validation is first a Nx target that runs on a workstation, then a family in tools/ci/families.mjs, never a condition on paths in the YAML. A change of .github/workflows/, tools/ci/, nx.json or of the tags updates the design of the CI.
  • node tools/ci/health.mjs gives the failure rate and the median duration of each job over the last 50 runs of main.

The reference images of the examples

Section titled “The reference images of the examples”

Each live example of the documentation is rendered in headless Chromium, on WebGL2 and on WebGPU, both on SwiftShader, and its canvas compared to a reference image (apps/docs/tests/screenshots/):

The examples run with their clock stopped and stop after a few frames (?time=1.5&frames=10): the image is the same at every run.

When a change modifies what an example draws, update its references, look at them, and commit them with the change. If the CI renders a little differently from your machine, run the Documentation workflow by hand with update-screenshots: it renders the references on the CI machine and gives them as an artifact. When a comparison fails, the report with the images of the difference is an artifact of the run.

Before submitting

Section titled “Before submitting”

Work on a branch, and open a pull request: main only receives squashed pull requests.

npm install with another version of Node writes the lockfile otherwise: the CI then fails at its installation.
